## 본문

## 📝 현재 문제점

v2.12.0 → v2.13.0에서 구역 스키마가 하위호환 불가하게 변경됐습니다. 평면 4필드(`playgroundCenter`, `playgroundRadiusInMeters`, `jailCenter`, `jailRadiusInMeters`)가 `areaType` 판별자 + `circle`/`polygon` 중첩 구조로 교체됐습니다.

이 때문에 신규 서버가 배포되면 이미 스토어에 배포된 앱(v2.3.7, 빌드 291)을 쓰는 유저는 아래 3가지 동작이 모두 실패합니다.

| 동작 | 엔드포인트 | 실패 원인 |
| --- | --- | --- |
| 방 만들기 | `POST /api/games` | `areaType`이 required로 추가됨 → 400 |
| 구역 조회 | `GET /api/games/{gameId}/area` | 응답에 평면 필드 없음 → 파싱 실패 |
| 구역 수정 | `PUT /api/games/{gameId}/area` | 요청 400 + 응답 파싱 실패 |

배포 순서를 바꿔도 해결되지 않습니다.

- 서버를 먼저 배포하면, 앱 심사 통과와 스토어 반영까지 수일간 구버전 유저 장애
- 앱 심사를 먼저 넣으면, 스토어 리뷰어가 프로덕션 서버로 신규 앱을 테스트하므로 구버전 서버에서 구역 파싱 실패 → 리젝

서버가 두 형식을 동시에 지원하면 양쪽 모두 해결됩니다.

### 영향 범위

두 명세를 기계 비교한 결과 전체 37개 엔드포인트 중 엔드포인트 추가·삭제 0건, 스키마 삭제 0건입니다. 스키마 4개 추가(`CircleAreaRequest`, `CircleAreaResponse`, `PolygonAreaRequest`, `PolygonAreaResponse`)와 기존 스키마 3개 변경이 전부입니다.

| 변경된 스키마 | 사용처 |
| --- | --- |
| `GameAreaRequest` | `POST /api/games`, `PUT /api/games/{gameId}/area` |
| `GameAreaResponse` | `GET /api/games/{gameId}/area` |
| `GameAreaUpdateResponse` | `PUT /api/games/{gameId}/area` 응답 |

로그인·게임 참가·채팅·게임 진행 등 나머지 34개 엔드포인트는 무관합니다. `AREA_UPDATED` 웹소켓 이벤트는 클라이언트가 payload를 파싱하지 않고 `GET /area`를 재조회하는 구조라 응답 수정으로 함께 해결됩니다.

## 🛠️ 해결 방안

### 1. 요청 폴백 — `GameAreaRequest`

`areaType`이 없으면 평면 4필드를 `CIRCLE`로 해석해 주세요. 이 하나로 `POST /api/games`와 `PUT /area`가 함께 해결됩니다.

```
areaType == null && playgroundCenter != null  →  CIRCLE 로 간주, 평면 필드 사용
areaType != null                              →  기존 v2.13.0 로직
```

구버전 앱이 보내는 요청

```jsonc
// POST /api/games
{
  "area": {
    "playgroundCenter": { "latitude": 37.5665, "longitude": 126.9780 },
    "playgroundRadiusInMeters": 500,
    "jailCenter": { "latitude": 37.5665, "longitude": 126.9780 },
    "jailRadiusInMeters": 100
  },
  "settings": { ... }
}
```

신규 앱이 보내는 요청

```jsonc
{
  "area": {
    "areaType": "CIRCLE",
    "circle": {
      "playgroundCenter": { "latitude": 37.5665, "longitude": 126.9780 },
      "playgroundRadiusInMeters": 500,
      "jailCenter": { "latitude": 37.5665, "longitude": 126.9780 },
      "jailRadiusInMeters": 100
    }
  },
  "settings": { ... }
}
```

신규 앱은 `areaType`을 항상 채우고, 해당하지 않는 쪽(`circle` 또는 `polygon`)은 직렬화에서 제외해 전송하지 않습니다. 따라서 `areaType` 유무로 구·신버전을 안전하게 구분할 수 있습니다.

### 2. 응답 가산 반환 — `GameAreaResponse`, `GameAreaUpdateResponse`

`areaType`이 `CIRCLE`일 때 중첩 구조와 평면 4필드를 동시에 반환해 주세요.

```jsonc
{
  "areaType": "CIRCLE",
  "circle": {                                    // 신규 앱이 읽음
    "playgroundCenter": { "latitude": 37.5665, "longitude": 126.9780 },
    "playgroundRadiusInMeters": 500,
    "jailCenter": { "latitude": 37.5665, "longitude": 126.9780 },
    "jailRadiusInMeters": 100
  },
  "playgroundCenter": { "latitude": 37.5665, "longitude": 126.9780 },  // 구버전 앱이 읽음
  "playgroundRadiusInMeters": 500,                                     // (deprecated)
  "jailCenter": { "latitude": 37.5665, "longitude": 126.9780 },
  "jailRadiusInMeters": 100
}
```

이 방식이 안전한 근거: 클라이언트가 JSON 파싱 시 모르는 키를 무시하도록 설정돼 있습니다(`disallowUnrecognizedKeys` 미사용). 구버전 앱은 `areaType`과 `circle`을 무시하고 평면 필드만 읽습니다.

### 3. POLYGON은 하위호환 대상이 아님

`POLYGON`일 때는 평면 필드를 채울 수 없으므로 중첩만 반환하면 됩니다. 구버전 앱에는 다각형을 렌더링·이탈판정할 코드가 아예 없어 하위호환이 원리적으로 불가능합니다.

다각형을 외접 원으로 근사해 평면 필드로 내려주는 방식은 사용하지 말아 주세요. 같은 게임에서 구버전은 원, 신규 앱은 다각형으로 판정해 동일 위치에서 한쪽만 구역 이탈로 처리되는 공정성 문제가 발생합니다.

클라이언트는 폴리곤 구역 생성 자체를 Remote Config 플래그로 잠가, 신규 앱 채택률이 충분해질 때까지 폴리곤 방이 만들어지지 않도록 대응합니다.

### 배포 순서

| 단계 | 담당 | 내용 |
| --- | --- | --- |
| 0 | 클라이언트 | 요청 헤더에 앱 버전·플랫폼 정보 추가, 폴리곤 생성 플래그 추가 (하위호환, 단독 배포) |
| 1 | **백엔드** | 위 1·2 적용 후 배포 |
| 2 | 클라이언트 | 신규 앱 심사 제출 → 승인 → 스토어 반영 |
| 3 | 클라이언트 | 채택률 확인 후 폴리곤 생성 플래그 활성화 |
| 4 | 양쪽 | 강제 업데이트로 구버전 차단 후 평면 필드·폴백 제거 |

1단계가 2단계보다 먼저여야 합니다. 그래야 스토어 리뷰어가 프로덕션에서 신규 형식을 받습니다.

4단계 제거 시점은 클라이언트가 강제 업데이트(Remote Config `minimum_version`)로 구버전 접근을 차단한 뒤 협의해 정하겠습니다.

- [ ] `POST /api/games` — `areaType: POLYGON` + `polygon` 중첩 요청 성공
- [ ] `GET /api/games/{gameId}/area` — CIRCLE 방 응답에 중첩·평면 필드 모두 포함
- [ ] `GET /api/games/{gameId}/area` — POLYGON 방 응답은 중첩만 포함

### 클라이언트에 공유 필요 (현재 서버 동작 확인)

- [ ] `circle`과 `polygon`을 동시에 채워 보낸 경우 — `GameAreaRequest`에 `oneOf`/`discriminator` 제약이 없어 둘 다 채워도 스키마 검증은 통과합니다. 400을 반환하는지, `areaType` 기준으로 한쪽만 읽는지 알려주세요. 클라이언트는 요청 조립 단계에서 타입 혼합을 자체 차단하므로 정상 경로로는 발생하지 않습니다.
- [ ] 폴리곤 꼭짓점 개수 검증 여부 — `PolygonAreaRequest`의 `playgroundPolygon`·`jailPolygon`에 `minItems`/`maxItems` 제약이 명세에 없습니다. 클라이언트는 3개 이상 10개 이하로 제한합니다. 서버 검증이 없으면 꼭짓점 2개(면적 0) 요청이 통과할 수 있습니다.
- [ ] 폴리곤 기하 검증 여부 — 자기교차 다각형 거부, 감옥 다각형이 플레이그라운드 다각형 내부에 완전히 포함되는지 검증. 클라이언트는 두 조건 모두 검증해 완료 버튼을 비활성화하지만, 서버 검증이 없으면 비정상 요청으로 구역이 생성될 수 있습니다.

후속 요청 3건

- [ ] `GameAreaRequest`의 `areaDataConsistent`·`legacyAreaDataValid` 필드를 명세에서 숨겨 주세요. 다른 필드와 달리 description·example이 없어 검증용 boolean getter(`isAreaDataConsistent()` 등)가 springdoc에 요청 필드로 노출된 것으로 보입니다. 클라이언트는 전송하지 않고 optional이라 동작 문제는 없지만, 명세를 코드 생성에 쓰면 존재하지 않는 요청 필드가 생깁니다. `@Schema(hidden = true)` 또는 `@JsonIgnore` 부탁드립니다.
- [ ] `PolygonAreaRequest`의 `maxItems`를 10으로 제한해 주세요. 현재 `2147483647`(int 최대값)이라 상한이 없습니다. 클라이언트는 꼭짓점을 3~10개로 제한하지만, API를 직접 호출해 꼭짓점 수백 개짜리 구역을 만들면 클라이언트가 그대로 렌더링을 시도합니다.
- [ ] 응답의 `areaType`을 항상 포함해 주세요. `GameAreaResponse`·`GameAreaUpdateResponse`의 `required`가 비어 있어 명세상 생략이 허용됩니다. 클라이언트는 `areaType`을 필수로 파싱하므로, 누락되면 구역 정보 로드가 실패합니다. 스키마의 required에 추가하거나 응답 계약으로 확정해 주시면 좋겠습니다.

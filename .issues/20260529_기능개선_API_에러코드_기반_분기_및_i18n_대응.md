## 제목

🚀 [기능개선][API][에러처리][i18n] errorCode 기반 실패 응답 분기 및 다국어 메시지 매핑 도입

## 본문

## 📝 현재 문제점

- 백엔드 실패 응답이 한글 고정 문구(detail)로 내려와, 영어/일본어 환경에서도 한글이 그대로 노출됨
- 에러를 구분할 식별자가 없어 detail 텍스트를 직접 비교해 분기하는 매직 스트링 의존 구조
- 백엔드 문구가 한 글자라도 바뀌면 프론트 분기 로직이 깨짐
- 현재 ApiErrorResponse는 RFC 7807(title/status/detail/instance)만 파싱하고 있어, 머신 식별자 기반 처리가 불가능함

## 🛠️ 해결 방안 / 제안 기능

- 백엔드가 추가하는 errorCode(SCREAMING_SNAKE_CASE) 필드를 응답 파싱 단계에서 수신
- errorCode를 기준으로 실패 케이스를 분기하고, 사용자 노출 문구는 ARB 기반 i18n 메시지로 매핑
- 백엔드가 내려주는 한글 detail은 errorCode 매핑이 없을 때의 fallback 용도로만 사용
- 신규 errorCode 추가 시 누락된 코드는 안전하게 fallback 처리되도록 방어

## ⚙️ 작업 내용

- 실패 응답 파싱 모델에 errorCode 필드 추가
- DioException 처리 흐름에서 errorCode를 AppException까지 전달하도록 연결
- 백엔드와 공유된 errorCode 목록을 프론트 분기/매핑 기준으로 정리
- errorCode → 다국어 메시지(ko/en/ja) 매핑 추가 (ARB 기반)
- 매핑이 없는 errorCode는 detail fallback 또는 공통 에러 문구로 처리
- 실시간 통신(STOMP) 에러 응답도 동일한 errorCode 체계 적용 여부 검토

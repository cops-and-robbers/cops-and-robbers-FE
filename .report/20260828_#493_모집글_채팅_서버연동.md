# 모집글 채팅을 예시 데이터에서 서버 연동으로 전환

### 📌 작업 개요
채팅 화면·상태 흐름은 #480에서 이미 완성돼 있었고, 저장소만 인메모리 목(`CommunityChatRepositoryMock`, 380줄)이었다. 대화가 앱 안에서만 살아 있어 앱을 껐다 켜면 사라지고 다른 사람과 이어지지 않았다. 이 이슈는 **데이터 출처 교체**다 — 인터페이스가 그대로라 화면과 Notifier는 서버가 REST로 주는지 소켓으로 주는지 알지 못한다.

작업 도중 백엔드가 두 번 움직였다. **#177(api-docs v2.24.0 → v2.25.0)** 이 채팅방 멤버 조회·강퇴·발신자 프로필 아이콘을 열었고, **#178** 이 STOMP 브로드캐스트에 빠져 있던 아이콘 필드를 채웠다. 후자는 이 작업 중 발견해 백엔드에 요청한 것이다.

**보고서 파일**: `.report/20260828_#493_모집글_채팅_서버연동.md`

### 🎯 구현 목표
- 채팅방 참여·나가기·이전 대화·내 채팅방 목록을 서버 연동으로 전환하고 목을 걷어낸다
- 실시간 채널을 구독한다 — 게임과 같은 연결 하나, 지금 보고 있는 방만
- 채팅 메시지 신고를 붙이되 신고 UI를 새로 만들지 않는다
- 실패 안내를 다국어로(ko/en/ja)

### ✅ 구현 내용

#### 데이터 계층 — DTO와 와이어 파서
- **파일**: `lib/features/community/data/models/community_chat_model.dart`(신규), `community_wire.dart`, `data/datasources/community_remote_datasource.dart`
- **변경 내용**: DTO 7종(api-docs v2.25.0) + Retrofit 5종(방 목록·참여·나가기·대화 내역·멤버 목록). `communityChatMessageBodyFromWire`가 `messageType` + `message`를 도메인 본문으로 읽는다
- **이유**: 서버가 본문 하나에 세 가지를 실어 보낸다 — `TEXT`는 문자열 그대로, `SYSTEM`·`GAME_INVITE`는 JSON 문자열이다. 읽을 수 없는 값은 전부 `unknown`으로 접는다: 던지면 새 타입 하나가 채팅방 한 장을 통째로 에러 화면으로 만든다(목록에서 `ENDED`가 추가됐을 때 실제로 그랬다). 서버가 빠뜨릴 수 있는 필드는 전부 nullable로 받는다 — 응답 한 건 때문에 대화 한 페이지가 날아가면 안 된다

#### 데이터 계층 — STOMP
- **파일**: `lib/features/community/data/datasources/community_chat_stomp_datasource.dart`(신규)
- **변경 내용**: `/subscribe/community/{postId}/chat` 구독, `/publish/community/{postId}/chat` 발행. 소켓 메시지 파싱에 REST DTO를 그대로 재사용
- **이유**: 게임과 같은 소켓 주소를 쓰고 어느 채팅인지는 구독 경로로 가른다. 구독은 보고 있는 방 하나뿐 — 목록에서 방마다 구독하면 방 100개에 구독 100개다. 발행 본문에 `messageType`을 빼면 서버가 400(`INVALID_MESSAGE_TYPE`)을 준다. #178 이후 소켓 payload와 REST 내역의 필드 이름이 같아져 DTO 하나로 둘 다 읽는다

#### 데이터 계층 — Repository
- **파일**: `lib/features/community/data/repositories/community_chat_repository_impl.dart`(신규), `community_chat_repository_mock.dart`(삭제)
- **변경 내용**: REST 5종 + 소켓을 한 인터페이스 뒤로. `connect()`가 메시지·연결 상태·에러를 한 스트림으로 합친다. 시각은 전부 `toLocal()`
- **이유**: 셋을 한 스트림에 실으면 Notifier가 구독 하나만 들고 있으면 된다. 시각을 안 맞추면 UTC로 파싱된 값이 그대로 떠서 한국 시간보다 9시간 이르게 보인다. 참여의 409(`ALREADY_JOINED`)는 성공으로 삼킨다 — 서버가 `chatJoined`를 주지 않아 앱이 참여 여부를 미리 알 수 없다

#### 소켓 수명과 재연결
- **파일**: `lib/features/community/presentation/providers/community_chat_room_provider.dart`, `domain/repositories/community_chat_repository.dart`
- **변경 내용**: `disconnect()` → `disconnect(int postId)`. `_attemptReconnect`에 `connecting`/`connected` 가드. 인증 에러코드면 재연결 전에 REST를 한 번 태운다
- **이유**: 방 A에서 B로 옮기면 A의 provider가 B보다 늦게 정리될 수 있다 — 방 번호를 확인하지 않으면 그때 막 붙은 B의 소켓이 끊긴다. 가드 한 줄이 둘을 동시에 막는다: 배너 "다시 연결" 연타, 그리고 STOMP ERROR 하나가 (에러 경로 + 뒤따르는 끊김 이벤트) 재연결을 두 번 거는 것 — 그래서 게임 채널의 `_isHandlingError` 같은 별도 플래그를 두지 않았다. 인증은 소켓만 다시 붙어봐야 계속 거절당한다: `TokenProvider.refreshAccessTokenIfNeeded`는 저장소를 다시 읽을 뿐이고(실측) 실제 재발급은 `AuthInterceptor`의 REST 401 경로에서만 일어난다

#### 강퇴 수신 (#177)
- **파일**: `community_chat_message_entity.dart`, `community_wire.dart`, `community_chat_timeline.dart`, `community_chat_preview_text.dart`, `community_chat_message_list.dart`
- **변경 내용**: `SYSTEM` 이벤트에 `KICK` 추가. 내 강퇴 메시지면 스스로 구독을 끊고 목록으로 나간다
- **이유**: 서버가 강퇴당한 쪽 세션을 끊지 않는다(Swagger 명시) — 앱이 안 끊으면 나간 방 메시지가 계속 들어온다(전송만 막힌다). enum에 값을 더했는데 `flutter analyze`가 조용해 소비처를 실측하니 셋 다 틀리고 있었다: 인원수 보정이 0, 미리보기와 시스템 pill이 강퇴를 "나갔어요"로 표시. 셋 다 삼항·기본값으로 흘리던 것을 **enum 전체 열거 switch**로 바꿔 다음에 이벤트가 늘면 컴파일이 먼저 깨지게 했다. 강퇴 문구는 게임 대기방의 "내보내졌어요"를 재사용

#### 채팅방 목록 신선도
- **파일**: `community_chat_rooms_provider.dart`, `community_chat_room_list.dart`, `community_page.dart`
- **변경 내용**: 채팅방에서 메시지를 주고받으면 목록의 그 방을 서버 왕복 없이 고치고 맨 앞으로(`applyLastMessage`). 스코프 전환·바텀 탭 복귀·앱 복귀에 목록을 다시 받는다(`refreshOnReturn`). 칸의 아바타를 `lastMessage.senderProfileIcon`으로
- **이유**: 목록 provider가 `keepAlive`라 방에서 대화하고 나와도 미리보기가 그대로였다. 채팅방은 루트 네비게이터에 push되므로 뒤로 가도 탭 위젯이 살아 있어 `initState` 갱신이 안 걸린다. 유효 시간은 두지 않았다 — 모집글 목록의 3분은 "실시간 데이터가 아니라 잠깐 낡아도 된다"는 근거 위에 선 값이고 채팅은 정반대다. 서버 지표에 호출량이 잡히면 그때 넣는다

#### 모임 정보 화면
- **파일**: `community_chat_meeting_info_page.dart`(신규, `community_chat_notice_page.dart`에서 rename), `route_paths.dart`, `app_router.dart`, ARB 3종
- **변경 내용**: 방장이 쓰는 채팅방 공지 → 모임 정보(모임 일시·장소·인원·모집글 본문). 저장소 인터페이스에서 `getNotice`/`setNotice` 삭제. 라우트 `/chat/notice` → `/chat/meeting-info`

- **이유**: 채팅방이 상세 provider를 같이 보고 있었는데 그쪽은 글·좋아요·댓글을 `Future.wait`로 함께 받아 하나만 실패해도 전부 에러가 된다. 채팅방에 필요한 건 글 하나뿐인데 댓글 조회가 실패했다고 상단 모임 카드가 사라지면 안 된다. 불필요한 요청 2건도 같이 사라진다

### 🔧 주요 변경사항 상세

#### 신고 가능 여부를 화면이 먼저 판정한다
`canReportChatMessage`가 넷을 거른다 — 내 메시지(서버 400 `SELF_REPORT`), 아직 전송 중(서버 id가 없다. 앱이 만든 `messageKey`를 대신 보내면 404 `CHAT_MESSAGE_NOT_FOUND`), 시스템 메시지·초대 카드(사람이 쓴 글이 아니다), 비로그인(내 메시지인지 가릴 수 없고 신고 자체가 401). 서버가 거절할 요청을 왕복시키지 않는다. 복사는 **필터를 거친 문자열**을 담는다 — 화면이 가린 말을 클립보드로 흘리지 않는다.

#### 소켓 payload 누락을 발견해 백엔드에 요청
#177이 발신자 프로필 아이콘을 REST 응답 세 곳(`MessageResponse`·`LastMessageResponse`·`MemberResponse`)에 추가하면서 네 번째 표면인 STOMP 브로드캐스트(`CommunityChatPayload`)를 빠뜨렸다. 그대로 두면 채팅방에 들어갔을 때는 아바타가 제대로 나오다가 이후 실시간으로 도착하는 메시지만 기본 아이콘으로 그려져, 같은 사람 말풍선이 위아래로 다른 얼굴을 단다.

앱에서 멤버 목록으로 메꾸는 우회와 정량 비교해 이슈로 올렸다 — 필드 추가는 메시지당 +22 B에 DB·스레드를 쓰지 않고, 앱 우회는 방 입장 1회 + JOIN마다 재조회(왕복당 DB 4쿼리·본문 621 B)에 새 멤버 첫 메시지가 기본 아이콘으로 뜨는 빈틈이 남는다. 손익분기는 재조회 1회 = 메시지 28건분. 결정적 근거는 지표가 아니라 **소켓 payload에 `senderNickname`은 이미 실려 있다**는 점이었다 — 성격이 같은 두 필드 중 하나만 빠진 것이라 설계가 아니라 누락이다. #178로 반영됐다.

#### 목록 실시간은 서버 없이 못 한다
내 모임 목록을 보고 있는 동안 다른 방에 온 메시지는 알 수 없다. 목록 화면의 앱은 어느 방도 구독하지 않고(방마다 구독 금지), 서버에 유저당 알림 채널이 없다. 전 방 구독은 계약 위반이고 앱을 껐다 켜면 어차피 놓치는 반쪽짜리다. 유저당 알림 채널을 백엔드에 요청할 대상으로 남긴다.

### ⚠️ 남은 것
- **읽음 표시·안 읽은 개수**: 읽음 표시는 서버가 상태를 만들지 않아 불가. 안 읽은 **개수**도 보고 있는 방만 구독하므로 셀 수 없다. "새 메시지 점"(목록 `lastMessage.id` vs 기기 저장 값)은 가능하나, 서버 알림 채널이 오면 버릴 코드라 넣지 않았다
- **미매핑 errorCode 7종**: 강퇴 3종(`FORBIDDEN_NOT_CHAT_HOST`·`CANNOT_KICK_SELF`·`CHAT_MEMBER_NOT_FOUND`)은 강퇴 UI 이슈에서, 좋아요·스크랩 4종은 #494에서 해소
- **강퇴 UI·`chatJoined` 버튼 문구**: 서버는 #177로 열렸으나 시안 확인이 먼저라 별도 이슈
- **참여 여부 우회**: `chatJoined`가 없어 상세에서 무조건 참여 요청을 보내고 409면 입장으로 잇는다. 버튼 문구를 "채팅 참여하기"/"채팅방 입장"으로 나누지 못한다

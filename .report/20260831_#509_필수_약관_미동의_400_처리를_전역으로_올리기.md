# 필수 약관 미동의(400) 처리를 전역으로 올리기

### 📌 작업 개요
BE #184(Swagger v2.28.0)가 필수 약관 미동의 검사를 게임 생성·참가 두 서비스에서
`TermsAgreementInterceptor`의 `/api/**` 전역으로 올렸다. 같은 PR이 어드민 재동의
수단(`resetTermsAgreement`)도 함께 넣었으므로, 이제 어드민이 플래그를 내리면
**어느 API를 부르든** `REQUIRED_TERMS_NOT_AGREED` 400이 온다.

그런데 앱은 이 errorCode를 게임 생성(`session_creation_flow_page.dart`)과 방 참가
(`home_page.dart`) **2곳에서만** 처리하고 있었다 — 정확히 인터셉터 이전의 서버 검증
지점 두 곳이다. 핸들러가 둘뿐인 건 실수가 아니라 **그때는 그게 정확한 범위**였고,
범위가 어긋난 건 서버가 넓어진 순간이다.

결과적으로 재동의를 실제로 돌리면 커뮤니티·마이페이지·공지에서는 일반 에러 스낵바만
뜨고 약관 화면으로 갈 길이 없다. 기능이 안 되는 게 아니라 **왜 안 되는지 알 수 없는**
상태가 된다.

**보고서 파일**: `.report/20260831_#509_필수_약관_미동의_400_처리를_전역으로_올리기.md`

| 진입 화면 | 개선 전 | 개선 후 |
|---|---|---|
| 게임 생성 · 방 참가 | 안내 + `/agreement` 이동 | 안내 + `/agreement` 이동 |
| 커뮤니티 · 마이페이지 · 공지 | 원인 모를 에러 스낵바, 이동 없음 | 안내 + `/agreement` 이동 |
| 게임 결과 조회 | 원인 모를 에러, 이동 없음 | 안내 + `/agreement` 이동 |

### 🎯 구현 목표
- 처리를 화면별 호출이 아니라 HTTP 클라이언트 한 곳으로 올린다
- 판정은 상태 코드가 아니라 errorCode로 (로케일 무관)
- 약관 제출 자체는 이 처리를 타지 않는다
- 에러를 삼키지 않는다 — 호출부의 로딩 해제·상태 정리가 계속 돌아야 한다

### ✅ 구현 내용

#### 1. `RequiredTermsInterceptor` — 감지만 하고 비켜준다
`onError`에서 errorCode를 보고 콜백을 부른 뒤 **`handler.next(err)`는 조건 블록 밖**에
둔다. 인터셉터가 처리했다고 `resolve`하면 화면의 `finally`·로딩 해제가 통째로 죽는다.

경로 비교는 `requestOptions.path`가 아니라 `uri.path`를 쓴다 — 쿼리스트링이 붙어도
제외 판정이 유지된다.

#### 2. 배선 — Auth 뒤
`dio_client.dart`의 인터셉터 목록에서 `AuthInterceptor` **다음**에 넣었다.
`AuthInterceptor`는 재발급 후 재시도를 인터셉터 없는 `_plainDio`로 보내지만, 그 실패를
`handler.next(...)`로 체인에 되돌린다. 그래서 뒤에 두면 재발급 경로의 400도 잡힌다.
BE `WebConfig`의 `Auth → Terms → QueryParameter`와 같은 순서다.

#### 3. 안내는 목적지 화면이 소비
인터셉터에는 `BuildContext`가 없어 스낵바를 그 자리에서 못 띄운다. 이 저장소는 이미
같은 답을 갖고 있다 — 강제 로그아웃이 `forceLogoutMessageKeyProvider`에 사유 키만 넣고
`login_page`가 진입 시 1회 읽고 지우며 표시한다. 같은 모양으로
`requiredTermsBlockedProvider`를 두고 `agreement_page`가 소비한다.

`core → feature` 역전도 기존 `ForceLogoutCallbackNotifier`와 같은 모양
(`RequiredTermsCallbackNotifier`)으로 맞춰 `lib/core/network`의 feature import를
0건으로 유지했다.

#### 4. 화면 호출부 2곳 축소
`handleRequiredTermsErrorIfNeeded`를 지우고 `isRequiredTermsMissingError`로 조기 반환만
남겼다. **그냥 지우면 안 된다** — 일반 에러 스낵바가 리디렉트 직전에 떠서, 없애려던
"원인 모를 에러"가 오히려 두 화면에 새로 생긴다.

`agreement_error_handler.dart`는 판별부만 남아 `flutter/material`·`riverpod`·
`AppSnackbar`·`features/auth` 의존이 전부 빠졌다.

### 🔧 주요 변경사항 상세

#### 판별부는 이미 분리돼 있었다
이슈의 "판별부를 전역에서 쓸 수 있게 분리"는 새로 쓸 게 아니었다.
`isRequiredTermsMissingError`가 이미 있었고 lib 어디서도 안 쓰이는 상태였다
(테스트만 참조). 그대로 썼다.

#### 제외 경로는 3개가 아니라 1개다
이슈는 "서버 제외 경로는 이 처리를 타지 않게 한다"라고 3경로를 함의한다.
`docs/api-docs.json` v2.30.0을 보니 `PUT /api/user/agreements`에 이 errorCode 예시가
붙어 있어 BE를 확인했다.

- `WebConfig`는 `/api/auth/**`·`/api/user/me`·`/api/user/agreements`를 인터셉터에서 뺀다
- 그런데 `UserService.updateTermsAgreement`가 필수 항목이 모두 true가 아니면 같은
  errorCode를 **직접** 던진다 — 즉 약관 제출 경로만은 인터셉터 밖에서도 이 코드를 낸다
- 나머지 두 경로는 이 코드를 낼 REST 코드 경로가 서버에 없다

그래서 제외는 `/api/user/agreements` 하나만 적었다. 도달할 수 없는 목록을 적으면 서버가
바뀌어도 아무도 고치지 않아 썩는다. (`CommunityChatService`도 같은 코드를 던지지만 STOMP라
Dio를 타지 않는다 — 커뮤니티 채팅 전송은 여전히 문구만 보이고 리디렉트가 없는 사각지대이며,
이 이슈 범위 밖이다.)

#### 안내 플래그가 샐 수 있는 자리 — 리뷰에서 잡음
처음 구현은 플래그를 무조건 켜고 콜백을 `?.call()`했다. 리디렉트가 no-op이 되는 경로가
셋 있다 — 콜백 미등록, `markNeedsAgreement`의 `state == null` 조기 반환, 이미
`requiresAgreement == true`인 경우.

이때 플래그만 `true`로 남는다. 이 값을 내리는 곳이 약관 화면 하나뿐이었으므로, 같은 앱
세션에서 **신규 가입자가 약관 화면에 들어오면 빨간 "필수 약관은 모두 동의해야 해요"**가
뜬다. 남의 세션 에러가 새 사용자에게 새는 형태다.

두 곳을 고쳤다 — 콜백이 없으면 플래그도 세우지 않고(로그만 남긴다), 로그아웃
(`signOut`·`forceLogout`)에서 기존 일회성 리셋들 옆에서 함께 지운다.

#### 전역 Dio가 하나가 아니다
`gameResultDioProvider`는 "이 요청의 401이 앱 전체 강제 로그아웃으로 번지면 안 된다"는
이유로 분리된 별도 Dio다. 그래서 이 처리도 함께 빠져 있었는데,
`GET /api/game-results/{gameResultId}`는 BE 제외 목록에 없어 재동의 상태면 400이 온다.
분리 사유(401 격리)와 약관 리디렉트는 다른 관심사이므로 인터셉터를 붙였다.
**인터셉터를 하나 다는 것만으로 "전역"이 되지 않는다** — 별도 클라이언트를 세야 한다.

#### 인터셉터 순서는 테스트 두 개로 잠근다
이 작업에서 가장 깨지기 쉬운 계약인데 처음엔 테스트가 0개였다. 행위 테스트
(401 → 재발급 200 → 재시도 400이 인터셉터에 도달)만으로는 부족하다 — 그 테스트는 자기
Dio를 만들어 쓰므로 `dio_client`의 실제 배선 순서를 못 본다. `DioClient.create` 결과에서
인덱스를 비교하는 구조 테스트를 따로 뒀다.

### 📌 참고사항
- **억제는 여전히 화면별 opt-in이다.** 감지는 전역화됐지만, 자기 에러 스낵바를 건너뛰는
  처리는 두 화면에만 있다. 다른 화면은 자기 스낵바를 띄운 뒤 리디렉트된다 —
  `AppSnackbar.show`가 첫 줄에서 `dismiss()`를 부르므로 겹쳐 쌓이지는 않고 깜빡임으로
  끝난다. 구조적으로는 이슈의 문제의식이 절반만 해소된 상태다.
- **BE 제외 목록과 짝이다.** `AuthNotifier.build()`가 cold start에서 `/api/user/me`와
  `GET /api/user/agreements`를 부르므로, BE가 `/api/user/me` 제외를 풀면 이 처리가
  AuthNotifier의 초기 조회에서 깨어난다. 이 결합은 인터셉터 주석에 남겼다.
- Riverpod에서 인터셉터 콜백이 provider를 수정하는 것은 안전하다 — 네트워크 응답은 언제나
  `await` 뒤라 동기 build 창 밖이다. 다만 테스트에서 provider build 중에 부르면
  assertion에 걸리므로 호출 시점을 실제와 맞춰야 한다.

# 커뮤니티 채팅 목록 실시간화 — 유저당 알림 채널·안 읽은 개수·방별 음소거

### 📌 작업 개요

내 모임(채팅방 목록) 화면은 어느 방도 구독하지 않았다 — 계약 02("보고 있는 방만 구독",
DEC-0026)가 목록을 실시간에서 배제했고, 앱은 화면으로 **돌아오는 순간**마다
`GET /chat/rooms`를 다시 받는 식으로 버텼다(`refreshOnReturn` 4경로). 사이드바의 종
아이콘은 서버에 보낼 곳이 없어 로컬 상태였다.

BE #182(Swagger v2.26.0, DOC-0044)가 셋을 열었다 — 유저당 알림 채널
`/subscribe/user/{userId}/community/chat`(DEC-0045), `ChatRoomResponse.unreadCount`와
`POST /{postId}/chat/read`(DEC-0044), `PUT /{postId}/chat/notification`과
`CommunityChatMemberListResponse.notificationEnabled`. 이 작업은 이 세 계약을 앱에
반영해 목록을 실시간화한다.

**보고서 파일**: `.report/20260831_#502_채팅_목록_실시간화_유저당_알림_채널_안_읽은_개수_방별_음소거.md`

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 목록 실시간성 | 방 밖에서는 소켓이 없어 새 메시지가 안 보인다. 화면 복귀 시에만 재조회 | 유저당 알림 채널로 미리보기·순서·+1을 그 자리에서 반영 |
| 안 읽은 개수 | 서버 개념 없음(로컬 상태 없음) | 서버 `unreadCount`가 기준선, 소켓 이벤트로 +1, 읽음은 `POST /chat/read`로 서버 커서 이동 |
| 방별 음소거 | 화면마다 임시 로컬 provider | 서버에 저장(`PUT /chat/notification`), 사이드바 종이 서버 값을 그린다 |
| 소켓 수명 | 방 화면 진입~이탈(08-24 스펙 "화면 수명 소켓") — 방을 나오면 개인 채널도 같이 죽는다 | 로그인~로그아웃. 방 나가기는 방 구독만 해제, 소켓은 유지 |

### 🎯 구현 목표

- 목록 화면이 켜져 있는 채로 다른 방의 새 메시지를 그 자리에서 반영한다(미리보기·순서·개수).
- 안 읽은 개수: 서버 `unreadCount`가 기준선, 소켓 이벤트로 +1, 읽음은 `POST /chat/read`로
  서버 커서를 이동.
- 방별 음소거를 서버에 저장하고 사이드바 종이 서버 값을 보여준다.
- 소켓 수명을 화면 → 로그인~로그아웃으로 옮긴다. 방 나가기는 방 구독만 해제한다.
- 목록 복귀 시 재조회 4경로를 없앤다.

### ✅ 구현 내용

이 설계는 세 갈래에서 "확장하지 않고 그대로 둔다"를 사용자가 판정했다 — 전부 코드
문제가 아니라 상한을 넘어서는 지점에 대한 판단이다.

① **게임 중 커뮤니티 소켓 공존은 그대로 둔다.** 게임 `chat`·`lobby`·`gameEvent`와
커뮤니티가 각자 `StompClient`를 열고 있어(소켓 통합은 이 이슈 밖) 게임 참가자당 연결이
+1 된다. 상한은 하트비트 스레드 부하(DOC-0037 §1)이고, 뒤집힐 지점은 소켓 통합 이슈다.

② **읽음은 진입 1회 + 이탈 1회.** 방 진입 시 첫 페이지 로드 뒤 `markRead(최신 id)`,
이탈 시 `PopScope`에서 새 메시지가 왔을 때만 한 번 더(`markReadOnExit`) — 같은 id면
생략한다. `community_notification_page.dart`(ISS-0157 선례)와 같은 모양이다.

③ **음소거 방의 개수는 그대로 표시한다.** 목록 API 응답에는 음소거 상태가 없다
(`notificationEnabled`는 멤버 목록 응답에만 있다) — 방마다 시각적으로 구분하려면 방
개수만큼 멤버 API를 따로 불러야 한다. 카카오톡처럼 안 읽은 개수는 음소거 여부와 무관하게
그대로 보여준다.

#### ① 계약 매핑 3필드

모델 3필드 — `unreadCount`(방 목록 응답), `communityPostId`(소켓 payload),
`notificationEnabled`(멤버 목록 응답) — 와 요청 DTO 2종(`CommunityChatReadRequestModel`,
`CommunityChatNotificationRequestModel`), Retrofit 2종(`readChat`, `updateChatNotification`)을
추가했다. 엔티티 쪽은 `CommunityChatRoomEntity.unreadCount`, `CommunityChatMessageEntity.isSystem`
+ `countsAsUnread` getter, 신규 `CommunityChatMembersEntity{notificationEnabled, members}`,
`CommunityChatEvent.message(postId, message)`로 postId를 실어 나른다.

저장소 인터페이스를 "소켓 열기/닫기"(`connect(userId)` / `disconnect()`)와 "방
구독/해제"(`subscribeRoom(postId)` / `unsubscribeRoom(postId)`)로 갈랐다 — 08-24 스펙이
방 화면에 몰아 뒀던 소켓 소유권을 분리하는 이 설계의 전제다. `CommunityChatPayload`의
`communityPostId`가 없는 payload는 이벤트를 버리고 로그만 남긴다 — 개인 채널은 이 키가
없으면 어느 방 이벤트인지 알 수 없다(LSN-0024).

#### ② 소켓 수명 재배치·소켓 Notifier

`CommunityChatSocketNotifier`(keepAlive)를 신설했다 — `currentUserIdProvider`를 듣다가
id가 생기면 `connect`, null이면 `disconnect`, id가 바뀌면 `disconnect` 후 `connect`(계정
전환). `lifecycleStateProvider` resumed → `reconnectNow()`. 재연결 정책(백오프
1·2·4·8·10초, 5회 소진, in-flight 무시, 인증 에러 시 REST 한 번으로 토큰 재발급 유도 후
재시도)을 방 Notifier에서 이 Notifier로 **이사**했다(복제가 아니다).

`main.dart`의 `MyApp.build`에 `ref.listen(communityChatSocketProvider, (_, _) {})` 한
줄로 살린다 — keepAlive는 "안 사라짐"만 보장하고 "watch하는 provider가 바뀌면
리빌드됨"은 보장하지 않는다. 리스너가 없으면 Riverpod의 예약된 리빌드가 지연된다는 것을
Riverpod 2.6.1 `ProviderScheduler` 소스까지 내려가 실측으로 확인했다(Task 3).

STOMP datasource의 `connectAs(wsUrl, token, userId)`는 `onConnected()`에서 유저 알림
채널과 예약된 방 채널을 **둘 다** 다시 구독한다(재연결 대응). `unsubscribeRoom`은
`_pendingPostId == postId`일 때만 실제로 구독을 해제한다 — 방 A→B 전환 시 늦게 도착한
A의 정리 요청이 이미 구독 중인 B를 끊지 않도록 하는 가드로, ISS-0155가 방 Notifier에
두던 이 가드를 datasource로 옮겼다.

#### ③ 방 구독/해제와 읽음

방 Notifier는 이제 구독/해제만 한다 — 연결·재연결·`reconnectExhausted`는 전부 소켓
Notifier로 위임했고 화면이 소켓 Notifier를 직접 watch한다. 진입 시 첫 페이지 로드 뒤
`markRead(postId, 최신 id)`(빈 방은 생략) → 성공하면 목록 `clearUnread(postId)`. 이탈은
방 화면을 `PopScope`로 감싸 `didPop`에서 `markReadOnExit()`(타임라인의 최신 서버 id가
마지막으로 보낸 id보다 클 때만 POST 1회) → `clearUnread`. pop 콜백은 `await` 전에
`ProviderScope.containerOf(context, listen: false)`를 미리 잡아 그 컨테이너로 읽는다
(LSN-0021, `community_notification_page.dart:68` 선례 — pop 도중 죽은 `context`의 `ref`를
쓰지 않는다).

강퇴(`KICK`이 나를 지목)·`NOT_A_CHAT_MEMBER`·`leave()` 성공 뒤에도 `unsubscribeRoom`을
부른다 — 방 구독만 해제되고 소켓 자체는 유지된다.

#### ④ 목록 +1·기준선 재동기화·4경로 정리·배지

`applyIncoming(postId, message)`는 목록에 있는 방이면 미리보기 교체 + 맨 앞 이동을 하고,
+1은 `senderId != 내 id && !isSystem && id > lastMessage.id`일 때만 센다(DEC-0044 서버
집계 쿼리와 같은 규칙 — 내 메시지·SYSTEM 제외, GAME_INVITE·미지 타입은 포함). 목록에
없는 방(방금 참여한 방)은 건드리지 않는다 — 다음 조회가 채운다.

**`_needResync`** — "다음 `connected`가 오면 서버 기준선을 다시 받아야 하는가"를 든
플래그다. **빌드 시점**에 소켓의 **현재 연결 상태**로 초기화한다: 이미 `connected`면
(흔한 경로 — 로그인 후 탭 진입, 에러 재시도 등으로 인한 invalidate 재빌드) 그 연결이
계속 유효하므로 `false`로 시작해 이중 조회를 막는다. 아직 안 붙었거나 끊긴 채로
빌드되면, 지금 받아 오는 기준선이 구독이 확립되기 전 스냅샷일 수 있어 `true`로 시작해
다음 `connected`에서 한 번 맞춘다. `disconnected` 이벤트가 오면 `true`로 세팅하고,
`connected` 이벤트가 오면 플래그를 확인해 끈 뒤(첫 로드가 아직 진행 중이면 그 로드
자체가 이미 최신 기준선이라 호출은 생략) `_resync()`를 부른다.

이 판정이 필요했던 이유는 provider의 **재빌드**(에러 재시도 `invalidate`, 방을 나간 뒤
`invalidate`)가 실제 소켓 재연결이 아닌데도 재연결로 오판돼 재동기화를 건너뛰거나
중복시키는 두 번의 실패를 거쳐서다: 1차로 시도한 "시간 기반 가드(`hasValue`)"는 스트림이
두 겹(연결 스트림 → 소켓 `events`)을 거쳐 도착하는 타이밍상 이벤트가 올 때 항상 참이 돼
매 연결마다 이중 fetch가 났다. 2차로 시도한 "빌드 후 첫 `connected` 생략" 플래그는
invalidate 재빌드가 그 플래그를 리셋해 버려, 다음에 오는 **진짜** 재연결의 재동기화를
조용히 삼켰다(리뷰에서 적발). `_needResync`는 판정 기준을 provider의 빌드 횟수가 아니라
소켓의 실제 연결 상태로 옮겨 이 둘을 모두 통과한다.

재조회 4경로 — `community_page.dart`의 `_refreshIfStale()`(탭 복귀·앱 복귀·정렬 전환
세 리스너가 공유하는 mine 분기)와 `community_chat_room_list.dart`의 `initState` — 를
전부 정리했다. 탭 복귀·앱 복귀는 `socket.reconnectNow()`(이미 붙어 있으면 무동작)로
바뀌었고, 정렬 전환·`initState`는 그냥 지워졌다. 이제 목록은 화면에 돌아올 때마다
GET을 다시 부르는 대신, 소켓이 끊겼다 다시 붙을 때만(또는 사용자가 당겨서) 재조회한다.

타일 배지는 `unreadCount > 0`일 때만 알약을 그린다(`AppColors.red` 배경,
`AppTextStyles.tag_12`, 흰 글씨), 99 초과는 `99+`(숫자 표기라 ARB에 넣지 않는다).
대화가 없는 방(`lastMessage == null`)은 개수도 0이다.

#### ⑤ 음소거

`communityChatMembersProvider(postId)`를 `CommunityChatMembersNotifier`
(`@riverpod class`, autoDispose family — 사이드바를 열 때마다 새로 받는 지금 수명 그대로)로
바꿨다. 상태는 `CommunityChatMembersEntity{notificationEnabled, members}`.
`toggleNotification()`은 낙관적으로 뒤집고 `setNotification`을 부른다 — `AppException`이면
(dispose되지 않았을 때만) 되돌리고 rethrow해 화면이 스낵바를 띄운다.

사이드바(`community_chat_room_info_page.dart`)의 로컬 `_chatNotificationEnabledProvider`를
지우고 서버 값(`notificationEnabled ?? true`)을 그린다. 종 탭 → notifier 호출, 실패 시
`AppSnackbar.show`.

  실시간으로 안 바뀌고 방 화면은 정상이면 이 지점을 의심 — 서버 로그의
  `CommunityStompInterceptor` user 경로 소유자 검증과, 앱이 보낸 `userId`가 로그인 id와
  일치하는지 대조한다.

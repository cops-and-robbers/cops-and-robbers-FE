# 모집글 좋아요·스크랩을 목데이터에서 서버 연동으로 전환

### 📌 작업 개요
좋아요·스크랩 토글 API(#170)는 이미 있었지만 게시글 응답에 카운트(`likeCount`·`scrapCount`)와
내 반응(`liked`·`scrapped`)이 실리지 않아, 버튼의 처음 상태를 그릴 수 없었다. 앱은
`CommunityInteractionRepositoryMock`(63줄, `postId * 3 % 47` 같은 계산으로 값을 지어냄)으로
버티고 있었고, 그 결과 같은 글이 목록에서 `0`, 상세에서 `37`로 보이는 상태였다.

백엔드에 응답 필드 4종을 요청해 착수 대기 상태로 시작했고(#187, api-docs v2.26.0 → v2.27.0),
필드가 `CommunityPostResponse` 한 스키마에 실려 왔다 — 별도 반응 조회 엔드포인트는 만들지 않았다.

**보고서 파일**: `.report/20260829_#494_모집글_좋아요_스크랩_서버_연동.md`

### 🎯 구현 목표
- 좋아요·스크랩을 메모리 목에서 서버 연동으로 전환하고 목을 걷어낸다
- 내 스크랩 목록 화면을 새로 만든다
- 좋아요·스크랩 관련 errorCode를 다국어 문구로 매핑한다

### ✅ 구현 내용

#### 데이터 계층 — 모델·엔티티
- **파일**: `community_post_model.dart`, `community_post_entity.dart`
- **변경 내용**: `likeCount`·`scrapCount`·`liked`·`scrapped` 4필드를 `required`로 추가. 와이어 키는
  `likeCount`·`scrapCount`·`isLikedByRequester`·`isScrappedByRequester`이며 뒤 둘은
  `@JsonKey(name:)`로 매핑한다.
- **이유**: 서버가 목록·단건·내 스크랩 목록·생성·수정·상태변경 전 표면에서 이 4필드를 항상 채운다
  (DEC-0048). non-null로 받아, 서버가 빠뜨리면 파싱을 멈춘다 — nullable로 물러서면 "아무도
  안 눌렀다"는 틀린 화면이 에러 없이 뜬다.

#### 데이터 계층 — Repository
- **파일**: `community_reaction_repository_impl.dart`(신규), `community_repository_impl.dart`
- **변경 내용**: 좋아요·스크랩 토글 Repository 추가. `POST`가 409(`ALREADY_LIKED`)면, `DELETE`가
  404(`LIKE_NOT_FOUND`)면 성공으로 삼킨다(스크랩도 동일 쌍).
- **이유**: 409·404는 사용자가 원한 최종 상태가 이미 그것이다. 실패로 올리면 화면이 하트를
  되돌리며 "실패했어요"를 띄우는데 서버에는 반응이 남아 화면과 서버가 어긋난다. 판정은 상태
  코드가 아니라 errorCode 기준 — 409·404는 다른 이유(`POST_NOT_FOUND`)로도 온다.

#### 삭제 — 상호작용 목 계층
- **파일**: `CommunityInteractionRepository`·`Mock`·`Entity`·`communityInteractionRepositoryProvider`
- **이유**: 값이 게시글 응답에 실려 오므로 별도 조회 계층이 통째로 필요 없어졌다. 상세의 병렬
  조회가 3개 → 2개로 줄고, 목이 만들던 가짜 참여 인원도 함께 사라져 상세도 카드처럼 정원만
  표시한다.

#### 목록·상세 동기화
- **파일**: `community_detail_provider.dart`, `community_provider.dart`
- **변경 내용**: 토글 성공 후 `_syncFeedCard()`가 목록의 그 카드만 `replacePost`로 갈아끼운다.
  `ref.invalidate`가 아니라 `replacePost`인 이유는 커서 페이지네이션 때문 — 무효화는 0페이지부터
  다시 당겨 3페이지까지 내려온 사용자를 하트 한 번에 맨 위로 튕긴다. `ref.exists` 가드로 죽어있는
  family 인스턴스를 새로 빌드해 네트워크 조회를 유발하는 걸 막는다(채팅방 push 진입 경로 보호).
- **이유**: 상세→목록 왕복을 API 재호출 없이 즉시 반영하기 위함. 다른 기기·세션에서 바뀐 값은
  피드의 3분 스테일 윈도우 안에서는 못 따라가는데, 이는 의도한 트레이드오프다(실패 비용이 낮고
  인스타그램도 같은 패턴).

#### 내 스크랩 목록 화면
- **파일**: `community_scrap_model.dart`(신규), `community_scrap_page.dart`(신규),
  `community_scrap_provider.dart`(신규)
- **변경 내용**: 봉투가 피드와 다르다 — 피드는 중첩 `cursor{}`에 opaque 문자열, 스크랩은 평평한
  최상위 필드에 정수(스크랩 id)다. 카드는 표시 전용이라 소유자 메뉴(수정·마감·삭제)는 상세로
  라우팅한다. 상세를 갔다 돌아온 시점에 그 글만 다시 조회해 스크랩 해제 여부를 반영한다.
- **이유**: 봉투를 재사용하면 커서 파싱이 조용히 어긋난다. 카드에서 삭제 등을 직접 처리하지 않고
  빈 case로 흘리면 사용자가 "실행됐다"고 믿고 돌아가는 사고가 난다.

#### errorCode 매핑
- **파일**: `error_message_mapper.dart`, ARB 3종
- **변경 내용**: `ALREADY_LIKED`·`LIKE_NOT_FOUND`·`ALREADY_SCRAPPED`·`SCRAP_NOT_FOUND` 4종을
  `errorCodeReactionAlreadyApplied` 한 키로 매핑.

### 🔧 주요 변경사항 상세

#### 계약을 non-null로 받은 결정과, 그 결정이 한 번 무너졌던 일
서버가 필드를 빠뜨리면 파싱에서 멈추게 하는 쪽을 택했다 — nullable 폴백은 필드가 배포되는 날
지워야 할 코드고, 그 전까지는 "아무도 안 눌렀다"는 틀린 화면을 에러 없이 보여준다. 그런데
api-docs.json이 v2.27.0으로 갱신되기 전 시점의 낡은 전제("필드가 아직 없다")를 근거로 이
4필드가 `@Default` 폴백 + 잘못된 와이어 키(`liked`/`scrapped`, 실제는 `isLikedByRequester`/
`isScrappedByRequester`)로 되돌아가 있었다. 그 상태로는 서버가 뭘 보내든 내 반응이 항상
꺼진 것으로 파싱된다 — 그 공백을 메우려고 상세 조회에 피드 캐시를 훔쳐오는 우회
(`_withKnownReaction`)까지 붙어 있었다. 오늘 세션에서 원래 계약(`required` + 올바른
`@JsonKey`)으로 복원하고, 이제 필요 없어진 우회와 그 우회만 검증하던 위젯 테스트를 걷어냈다.

#### 목록 반영이 낙관적 갱신에 안전한 이유
`toggleLike`·`toggleScrap`은 응답을 기다리지 않고 먼저 뒤집는다. 실패하면 뒤집기 전 값으로
되돌리고 예외를 다시 던진다 — catch 밖에서 `_syncFeedCard()`를 부르는 이유는, 서버가 이미
반응을 받은 뒤에 던지면 catch가 그 성공을 롤백해 "서버는 됐는데 화면은 실패"로 어긋나기
때문이다.

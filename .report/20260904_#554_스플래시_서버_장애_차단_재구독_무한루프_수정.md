### 📌 작업 개요
서버 Env를 바꾼 뒤 스플래시가 "차단 화면 ↔ 스플래시 로고"를 계속 오가며 반복되는 문제 수정. #554에서 넣은 서버 장애 차단 화면이 자기 자신의 재구독 신호에 반응해 무한 재시도를 도는 회귀였다

**보고서 파일**: `.report/20260904_#554_스플래시_서버_장애_차단_재구독_무한루프_수정.md`

### 🔍 문제 분석
#554는 서버 장애로 차단할 때마다 기기 연결 상태 변화 스트림(`onConnectivityChanged`)을 구독해, 연결이 돌아오면 자동으로 재시도하게 했다. 그런데 `connectivity_plus`는 새 리스너가 붙을 때마다(Android `ConnectivityBroadcastReceiver.onListen`, iOS `ConnectivityPlusPlugin.onListen` 둘 다 소스에서 확인) **실제 변화가 아니라 그 순간의 현재 상태를 무조건 한 번 먼저 흘려보낸다.**

기기 WiFi/모바일 데이터는 계속 살아 있는 상태였으므로, 흐름은 다음과 같이 반복됐다:
1. 서버 장애로 차단(`ServerErrorPage`) → connectivity 재구독
2. 재구독 직후 플랫폼이 "지금 연결돼 있음"을 즉시 재생
3. 이걸 "연결 복구"로 오인해 전체 플로우를 다시 시도 — 연결 사전 체크는 통과하므로 차단을 먼저 풀고 스플래시 로고를 잠깐 그림
4. 여전히 응답 없는 서버 Env에 다시 부딪혀 실패 → 다시 차단 → 다시 재구독
5. 2번으로 돌아가 무한 반복

기기 네트워크나 플랫폼의 변덕과 무관하게, 자기 자신이 쏜 신호에 자기가 반응하는 결정론적 루프였다. 처음엔 `distinct()`로 "같은 값 반복 발화"를 걸러 시도했으나, 매번 새로 만들어지는 구독은 비교할 "이전 값"이 없어 재생 이벤트를 걸러내지 못했다.

### ✅ 구현 내용

#### connectivity 스트림의 첫 이벤트 무시
- **파일**: `lib/core/network/connectivity_service.dart`
- **변경 내용**: `onConnectivityChanged`에 `.skip(1)`(+ 기존 `.distinct()` 유지) 추가. 구독 시점에 플랫폼이 재생하는 첫 이벤트를 버리고, 그 이후의 진짜 변화만 통과시킨다
- **이유**: 이 스트림의 유일한 소비처가 스플래시라 국소적으로 안전하다. 진짜 오프라인→온라인 전환은 여전히 통과하므로 기존 자동 복구 동작은 유지된다

#### 테스트 페이크를 실제 플랫폼 동작에 맞춤
- **파일**: `test/core/network/connectivity_service_test.dart`
- **변경 내용**: `FakeConnectivity.onConnectivityChanged`를 `async*`로 바꿔 구독 시점에 현재 상태를 먼저 재생하도록 수정. 재생 이벤트가 걸러지는지 확인하는 테스트 추가, 기존 3건에는 재생 이벤트가 지나갈 시간을 주는 선행 `await` 추가
- **이유**: 기존 페이크는 구독해도 값을 재생하지 않아 이 버그 자체를 재현할 수 없는 구조였다. 실제 플랫폼과 다르게 동작하는 페이크가 회귀를 못 잡은 근본 원인이라 페이크를 먼저 고쳤다

#### 서버 5xx 경로 회귀 테스트 (신규)
- **파일**: `test/features/auth/presentation/pages/splash_server_error_loop_test.dart` (신규)
- **변경 내용**: `SplashPage` 전체를 실제로 띄우고, 게임 상태 조회가 항상 500을 던지도록 구성. 차단 후 8초를 흘려보내도 재시도 호출 횟수가 늘지 않는지 확인
- **이유**: 이 루프는 DNS 실패(네트워크성)든 5xx(서버성)든 같은 `_showBlock`/재구독 경로를 타므로, 처음 발견된 DNS 케이스뿐 아니라 서버가 살아서 5xx만 내는 경우도 같은 결함이 있는지 별도로 확인했다

### 🔧 주요 변경사항 상세

#### 근거: 네이티브 소스 확인
Android(`ConnectivityBroadcastReceiver.java`) 81~83행 주석: "시스템의 첫 변화를 기다리지 않고 첫 이벤트를 바로 내보내야 한다" — `sendEvent(connectivity.getNetworkTypes())`를 `onListen` 안에서 무조건 호출. iOS(`ConnectivityPlusPlugin.swift`)의 `onListen`도 동일하게 `connectivityUpdateHandler(currentConnectivityTypes)`를 즉시 호출한다. 두 플랫폼이 독립적으로 같은 설계를 택한 것으로, 짐작이 아니라 패키지 소스에서 직접 확인했다.

#### 회귀 재현 (RED → GREEN)
`skip(1)`을 임시로 빼고 두 테스트(스트림 유닛 테스트, 500 위젯 테스트)를 돌려 실패를 확인한 뒤 복원해 통과를 확인했다. 500 위젯 테스트 기준: 수정 전엔 8초 동안 재시도가 3회로 늘었고, 수정 후엔 1회로 고정됐다.

**특이사항**:
- `skip(1)`은 이 스트림의 유일한 소비처(스플래시)에만 영향. 다른 곳에서 `onConnectivityChanged`를 구독하게 되면 "구독 직후 첫 이벤트는 항상 버려진다"는 계약을 알아야 한다 — 서비스 파일 docstring에 이유를 남겨뒀다
- 실기기에서 서버 Env를 죽은 값으로 바꿔 차단 화면이 반복 재시도 없이 유지되는지 확인은 아직 못함(에뮬레이터/유닛 테스트로만 검증)

# Issue Mode — 이슈 본문 생성

대략적인 설명을 받아 **GitHub에 그대로 붙여넣을 제목 + 본문**을 만든다.
읽는 사람은 그 일을 할 개발자다 — 스크롤하기 전에 "뭘 해달라는 건지"가 보여야 한다.

## 사용자 입력

$ARGUMENTS

## 금지

- Edit/Write로 **코드 수정 금지** — 이슈 문서 저장만 한다
- 구현 코드를 대신 써주지 않는다. 코드는 *이미 있는* 코드를 근거로 가리킬 때만
- `🔥 [긴급]`은 사용자가 "긴급"이라고 말했을 때만
- 담당자 이름 임의로 채우기 금지 (템플릿 그대로 둔다)
- 추측을 사실처럼 쓰지 않는다 — 모르는 건 `❓ 확인 필요`로 넘긴다

---

## 1. 타입 판단

| 입력 신호 | 제목 | 템플릿 | 파일명 타입 |
|---|---|---|---|
| 안 됨·에러·깨짐·크래시·실패 | `❗ [버그][카테고리]` | `bug_report.md` | `버그` |
| 새로·구현·추가 | `⚙️ [기능추가][카테고리]` | `feature_request.md` | `기능추가` |
| 개선·변경·수정 | `🚀 [기능개선][카테고리]` | `feature_request.md` | `기능개선` |
| 제안·요청 | `🔧 [기능요청][카테고리]` | `feature_request.md` | `기능요청` |
| 디자인·UI·색상·레이아웃 | `🎨 [디자인][카테고리]` | `design_request.md` | `디자인` |
| 테스트·QA·검증 | `🔍 [시험요청][카테고리]` | `qa_request.md` | `시험요청` |

카테고리는 여러 개 가능하다 (`[버그][Flutter][빌드]`).
**타입이나 카테고리가 애매할 때만** 짧게 묻는다. 나머지는 문맥에서 판단한다.

## 2. 본문 뼈대

`.github/ISSUE_TEMPLATE/<템플릿>`을 읽어 그 섹션 구조를 뼈대로 쓴다.
**여기에 복사해두지 않는다** — 복사하면 템플릿이 바뀌었을 때 이 커맨드만 옛 구조를 들고 있게 된다.

- 헤딩은 `## 🗒️ 설명`처럼 `##` + 이모지로 옮긴다 (템플릿의 `---` 밑줄 스타일 대신)
- **해당 없는 섹션은 지운다.** 빈 껍데기를 남기지 않는다
- 뼈대에 없어도 필요하면 더한다:

| 섹션 | 언제 |
|---|---|
| `🔥 구현 기능` | 요청이 표 하나로 요약될 때 — 맨 위에 둔다 |
| `❓ 확인 필요` | 상대가 정해줘야 진행되는 것 (필드명·인증 방식 등) |
| `📌 참고` | 관련 이슈 번호, 일부러 범위에서 뺀 항목 |
| `🚧 작업목록` | `- [ ]` 체크박스 + 브랜치명 코드블록 |

## 3. 가독성

- **결론 먼저.** 첫 섹션에서 "무엇을 해달라"가 끝나야 한다. 배경·근거는 그 다음
- **셋 이상은 표로.** 필드·엔드포인트·Before/After는 불릿 말고 표
- **강조는 GitHub 알림으로** — `> [!WARNING]` 지금 깨져 있는 것 / `> [!IMPORTANT]` 놓치면 반쪽이 되는 조건 / `> [!TIP]` 선택 사항
- **긴 근거는 접어서.** 코드 인용·로그는 `<details><summary>`
- **`<sub>`·`<small>` 금지.** 글씨가 너무 작아 아무도 안 읽는다. 덧붙일 말이 중요하면 본문 크기로 쓰고, 안 중요하면 지운다
- **위치를 짚어서.** `CommunityPostService:170`처럼 파일·라인·이슈 번호로 쓴다. "어딘가에서" 금지
- 섹션 사이에 `<br>` 한 줄 — GitHub에서 숨 쉴 틈이 생긴다
- 굵게는 문장의 핵심 한 조각에만. 문단 전체를 굵게 쓰면 강조가 죽는다

## 4. 저장 · 출력

1. 제목 + 본문을 채팅에 출력한다 (그대로 복붙 가능하게)
2. `.issues/[YYYYMMDD]_[타입]_[간단한설명].md`로 저장한다
   예: `20260828_기능추가_모집글_반응_필드.md` (없으면 `.issues/` 생성)
3. 저장 경로 한 줄 안내로 종료. 추가 질문하지 않는다

## 🚀 [기능개선][커뮤니티] 모집글 목록 캐시 유효 시간 적용

### 📌 작업 개요

#477에서 목록을 스코프별로 캐시해 재조회를 없앴는데, 낡은 목록을 되돌릴 기준이 없어 게임 한 판을 하고 돌아와도 처음 받은 목록 그대로였다. 목록에 받아온 시각을 기록하고 3분이 지나면 낡은 것으로 판정해, 화면에 다시 들어오는 순간 조용히 다시 받는다. 3분 안에 돌아오면 캐시를 그대로 쓴다.

곁들여 검색 화면의 최근 검색어를 타이핑에 맞춰 좁혀 보여준다 — 로컬 목록을 거르는 것이라 서버 요청은 없다.

### 🎯 구현 목표

- 목록을 받아온 시각을 상태에 기록
- 화면이 다시 보이는 순간 경과 시간을 확인해 3분을 넘겼으면 재조회
- 재조회 트리거: 다른 탭·게임에서 커뮤니티로 복귀, 앱이 백그라운드에서 복귀, 이전에 본 정렬로 되돌아감
- 유효 시간 판정을 테스트할 수 있도록 시계를 갈아끼울 수 있게 분리

**캐시 폐기 방식(gcTime)을 쓰지 않은 이유**: `StatefulShellRoute.indexedStack`이 탭 위젯을 항상 살려 두어 구독자가 0이 되는 순간이 없다. "보는 사람이 사라지면 N분 뒤 폐기"는 이 앱에서 영원히 발동하지 않는다. 낡음 판정 후 재조회(staleTime) 방식이어야 한다.

### 🔧 주요 변경사항 상세

#### `refreshIfStale()` — 건드리지 않는 네 가지 경우

사용자가 부른 동작이 아니므로 조용히 갱신하고, 다음 경우엔 손대지 않는다:

| 가드 | 이유 |
|---|---|
| `state.valueOrNull == null` | 한 번도 성공한 적 없다 — 첫 로드 중이거나 첫 로드가 실패했다. 되살릴 목록 자체가 없다 |
| `isLoadingMore` | 페이지를 이어붙이는 중이면 그 요청을 버리게 된다 |
| `state.isLoading` | 갱신이 이미 진행 중. 없으면 두 트리거가 겹칠 때 요청이 한 번 더 나간다 |
| `items.length > _pageSize` | 여러 페이지를 이미 불러온 목록. 0페이지부터 다시 받으면 읽던 자리를 잃고 스크롤이 새 목록 끝으로 밀리며 `loadMore`까지 딸려 나간다 |

**특이사항**:
- **한 번 성공한 뒤 실패한 상태는 통과시킨다.** Riverpod의 `AsyncError`가 `copyWithPrevious`로 이전 성공 값을 그대로 들고 있어 `valueOrNull`이 non-null이다. 그게 맞는 동작이다 — 화면에 다시 들어오는 순간은 일시 장애로 실패한 조회를 재시도하기 가장 좋은 때다
- **배경 갱신 실패 시 이전 상태로 되돌린다.** 실패했다고 보고 있던 목록을 에러 화면으로 갈아치우면, 아무것도 안 누른 사용자가 지하철에서 목록을 잃는다. `fetchedAt`도 옛날 값이라 다음 복귀에 다시 시도한다. (당겨서 새로고침은 사용자가 요청한 것이라 `refresh()`가 그대로 에러를 화면에 반영하는 것이 맞다)

#### `MainScaffold` — 프레임 뒤로 미루는 provider 쓰기

`initState`와 `didUpdateWidget` **둘 다 위젯 트리 빌드 도중에 불린다.** 여기서 바로 provider를 쓰면 Riverpod가 "빌드 중 provider 수정" 어서션으로 막는다. `addPostFrameCallback` + `mounted` 가드로 프레임이 끝난 뒤로 미룬다.

브랜치 비교가 `didUpdateWidget`에서 정확히 되는 근거: `StatefulNavigationShell.currentIndex`는 위젯의 **final 필드**이고 브랜치가 바뀌면 go_router가 새 인스턴스를 만든다. 그래서 `oldWidget`과 값 비교가 성립한다.

#### 정렬 전환 트리거

정렬은 provider family 키의 일부라 정렬마다 별도 인스턴스이고, 키워드가 없는 목록은 `keepAlive`라 살아 있다. 그런데 정렬 전환은 브랜치 인덱스를 바꾸지 않는다 — 트리거가 없으면 한 번 본 정렬은 당겨서 새로고침 전까지 영원히 낡은 채로 남는다. 최종 리뷰에서 잡아 리스너를 추가했다.

#### `clockProvider`

```dart
DateTime Function() clock(Ref ref) => DateTime.now;
```

값이 아니라 함수를 담는 이유는 호출 시점의 시각을 원하기 때문이다. 시간은 시스템 경계라 테스트에서 갈아끼울 자리가 필요했다. 세 번째 사용처가 생기면 `core`로 옮긴다.

### 📊 성능 영향

이 작업은 호출을 줄이는 쪽이 아니라 **#477이 줄인 것 중 일부를 의도적으로 되돌리는** 쪽이다. 신선도를 사는 대가를 호출 수로 적는다.

측정 기준은 **목록 API 호출 횟수**이며 응답 지연(latency)은 재지 않았다. 아래 수치는 출처가 둘로 갈린다 — **#477 값은 계량 Repository로 실제 화면에서 잰 실측**이고, **#479 값은 가드 로직에서 계산한 값**이다.

#### 1. 출발점 — #477이 만든 것과 남긴 것

전체 범위로 N번 되돌아올 때 `N+1`회 → 1회, 감소율 `N/(N+1)`. 측정 시나리오(토글 왕복 3회)에서 **4회 → 1회, 75% 감소**.

그 대신 남은 것이 이번 이슈다. 줄인 3회는 전부 "낡은 목록을 그대로 보여준" 횟수였고, 그것을 되돌릴 기준이 없었다.

#### 2. #479가 되돌리는 양

세션 하나를 가정해 계산했다 — 커뮤니티 탭에 8회 진입, 그중 3분 이상 자리를 비운 뒤 복귀가 2회(게임 한 판 + 백그라운드 복귀 1회).

| | 목록 호출 | 캐시 적중 | 3분 넘게 낡은 목록을 본 횟수 |
|---|---|---|---|
| #477 이전 | 8 | 0회 (0%) | 0 |
| #477 이후 | 1 (**-87.5%**) | 7회 (87.5%) | **7** |
| #479 이후 | 3 (**-62.5%**) | 5회 (62.5%) | **0** |

감소율 **25%p를 내주고** 낡은 화면 7회를 0으로 만들었다. 일반형은 `1 + S`회 — S는 3분 이상 자리를 비운 뒤 복귀한 횟수이고, 진입 횟수 K보다 훨씬 작다.

#### 3. 재조회 1회에 실제로 나가는 것

호출 수를 목록 API로만 세면 실제 비용을 놓친다. #477 이전의 진짜 문제는 스코프를 토글할 때마다 국가 조회 provider까지 함께 폐기돼 **GPS 측정과 `/country`(Geoapify, 일 3,000건 한도 공유)가 딸려 나간 것**이었다. #479의 재조회가 같은 것을 끌고 가는지 확인했다.

| 정렬 | 목록 API | `/country` | GPS 측정 |
|---|---|---|---|
| 최신순 · 마감임박순 | 1 | **0** | 0 |
| 거리순 | 1 | **0** | 1 |

`/country`가 0인 근거: `communityCountryCodeProvider`는 `@Riverpod(keepAlive: true)`이고, `refresh()`는 `ref.invalidateSelf()`로 피드 인스턴스만 무효화한다. 재빌드가 `ref.watch(communityCountryCodeProvider.future)`를 다시 타도 캐시된 값이 즉시 돌아온다. 이 provider의 무효화 경로는 `CommunityFeedList._ensureLocationForDistance()`가 거리순 선택 시 위치 권한을 새로 얻었을 때 부르는 `ref.invalidate` 하나뿐이다.

**거리순만 GPS를 다시 잰다.** `build()`의 `_resolveSortCoordinates()`가 `currentPositionResolverProvider`를 다시 호출한다. 서버 호출은 아니지만 기기 측정 비용(최대 10초 타임아웃, `device_location_service.dart:20`)이 붙는다. 거리순을 켜 둔 채 자주 복귀하는 사용자에게는 개선 여지다 — 좌표도 유효 시간을 두고 재사용하는 방법이 있다.

#### 4. 전송량

#477에서 캐시 규모를 잴 때 나온 값이 그대로 쓰인다. 본문 1000자 상한 · 100건(5페이지)에서 약 0.34 MB이므로 **1페이지(20건) 최악 약 70 KB**. 재조회는 항상 0페이지 1장이므로 위 세션 가정에서 추가 전송량은 **최악 약 140 KB**다. 실제 본문은 상한보다 훨씬 짧아 이보다 작다.

#### 5. 3분이라는 값의 근거

라운드 제한 시간은 **최소 10분 · 기본 30분 · 최대 180분**이다(`step_2_game_settings_content.dart:79-82`). 유효 시간 3분은 **가장 짧게 설정한 게임보다도 짧다** — 어떤 설정으로 게임을 해도 끝내고 돌아오면 반드시 재조회된다. 이슈가 요구한 핵심 시나리오가 방 설정과 무관하게 성립한다.

반대쪽 경계도 같이 본다. 탭을 잠깐 오가거나 글 하나를 읽고 나오는 3분 미만 이동은 전부 캐시 적중이다. 상세·검색은 셸 위에 떠서 브랜치 인덱스를 바꾸지 않으므로 애초에 트리거되지도 않는다.

#### 6. 호출 상한

재조회에 성공하면 `fetchedAt`이 갱신되므로 같은 정렬 인스턴스는 재조회 사이에 최소 3분을 둔다 → **정렬 인스턴스당 시간당 최대 20회**. 노출 정렬이 셋(최신·거리·마감임박)이라 이론상 60회/시간이 상한이지만, 3분마다 정렬 셋을 전부 순회해야 나오는 값이다.

단, 재조회가 실패하면 `fetchedAt`을 옛 값으로 되돌리므로 **이 상한은 성공 기준이다.** 서버가 계속 실패하는 동안에는 타이머가 아니라 트리거 빈도가 재시도 간격을 정한다.

#### 7. 가드가 막아 주는 호출

`refreshIfStale()`의 가드 넷은 각각 실제 호출을 막는다.

| 가드 | 막는 것 |
|---|---|
| `state.isLoading` | 당겨서 새로고침 중 트리거가 겹칠 때 나가는 중복 요청 |
| `isLoadingMore` | 진행 중인 다음 페이지 요청을 버리고 다시 받는 왕복 |
| `items.length > _pageSize` | 2페이지 이상 읽은 사용자의 재조회 전부 — 스크롤 위치 손실과 그로 인한 `loadMore` 연쇄까지 |
| `valueOrNull == null` | 첫 로드가 끝나기 전 트리거가 울릴 때의 중복 요청 |

세 번째 가드는 특히 크다. 무한 스크롤을 많이 내린 사용자일수록 재조회 비용이 큰데, 그 구간을 통째로 0으로 만든다.

#### 8. 호출이 전혀 늘지 않는 경로

- **우리 동네 · 내 모임 범위** — 서버가 400을 주므로 원래 호출이 없다. 유효 시간은 사실상 전체 범위에만 적용된다
- **검색** — 키워드가 있는 인스턴스는 `keepAlive`가 아니라 화면을 나가면 폐기된다. 캐시가 없어 이 경로를 타지 않는다
- **최근 검색어 좁히기** — 로컬 목록 필터링이라 서버 요청 0. 백엔드가 반대한 실시간 검색 호출은 넣지 않았다

---

### 📌 참고사항

- **검색은 캐시하지 않는다.** 키워드가 있는 인스턴스는 `keepAlive`를 걸지 않아 검색 화면을 나가면 폐기된다. 같은 단어로 다시 검색하면 항상 새로 받는다 — 검색 결과는 목록보다 휘발성이 크다고 봤다
- **우리 동네·내 모임 범위는 호출 자체가 없다.** 서버가 아직 400을 주므로 확정 실패를 왕복시키지 않는다. 유효 시간은 사실상 전체 범위에만 적용된다
- **3분은 첫 값이다.** 실사용 후 조정 가능하며, `community_provider.dart`의 `_staleAfter` 한 곳만 고치면 된다
- 국가 조회는 위치 권한을 새로 얻었을 때만 다시 판정한다 — 목록 재조회가 국가 재판정을 끌고 가지 않도록 분리를 유지했다

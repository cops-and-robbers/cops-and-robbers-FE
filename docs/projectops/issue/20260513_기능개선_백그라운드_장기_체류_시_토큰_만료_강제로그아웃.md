## 제목

🚀 [기능개선][Auth][백그라운드] 게임 중 백그라운드 장기 체류 시 토큰 만료로 인한 강제 로그아웃 방지

## 본문

## 📝 현재 문제점

- 게임을 진행하다 앱을 백그라운드로 보낸 뒤 일정 시간(현재 백엔드 정책상 access token 만료 시간 이후) 머무르면, 복귀 시 첫 API 호출에서 401이 발생하고 토큰 재발급도 실패할 경우 강제 로그아웃됨
- 강제 로그아웃이 발동하면 토큰 삭제 + Firebase signOut + 로그인 화면으로 이동, 진행 중이던 게임에서 그대로 튕김
- 위 #346 이슈(ref disposed)와 동일한 "백그라운드 → 포그라운드 복귀" 흐름에서 함께 보고됨 (인과는 독립이지만 트리거 조건이 같아 자주 동반 관찰됨)

## 🔍 현재 동작 추적

관련 위치:

- `lib/core/network/auth_interceptor.dart` — 401 응답 처리 + 토큰 재발급 + 강제 로그아웃 트리거
- `lib/core/services/lifecycle/app_lifecycle_service.dart` — 백그라운드 keep-alive 메커니즘
- `lib/core/storage/secure_token_storage.dart` — JWT 토큰 영구 저장 (만료 판단 로직 없음)

강제 로그아웃이 발동되는 경로는 모두 `AuthInterceptor.onError`에 모여 있고, 다음 다섯 가지 케이스가 동일하게 `_handleForceLogout()`을 호출함:

1. `/api/auth/reissue` 자체가 401 응답 (refresh token 만료)
2. 이미 한 번 재시도한 요청이 다시 401 (`_isRetry` 플래그)
3. SecureStorage에 refresh token이 아예 없음
4. reissue 응답이 200이지만 `tokens` 필드 파싱 실패
5. reissue 호출에서 예외 (네트워크 끊김 포함)

`_handleForceLogout()`은 `tokenStorage.clearTokens()` + `onForceLogout()` 콜백(Firebase signOut + 로그인 화면 라우팅)을 실행함.

현재 keep-alive 메커니즘은 다음과 같이 동작함:

- 게임 시작 시 `AppLifecycleService.startBackgroundInfra()` 호출 → 백그라운드 진입 시 30초마다 `Geolocator.getCurrentPosition()`을 주기적으로 호출해 OS suspend를 방지
- 이 keep-alive는 OS가 앱을 suspend하지 않도록 "위치 콜백을 트리거"하는 것이 유일한 목적이며, 인증 토큰을 proactive하게 갱신하지 않음

`SecureTokenStorage`는 토큰을 단순 read/write만 함:

- 클라이언트가 JWT payload를 decode해 만료 시각을 검사하는 로직 없음
- 만료 판단은 서버가 401로 응답할 때만 수동적으로 일어남

즉 현재 정책상 백그라운드에 충분히 오래 머무르면:

- access token 만료 → 첫 API 호출 시점에 401
- refresh token도 만료됐을 가능성 → reissue 401 → 강제 로그아웃

## 🛠️ 해결 방안 / 제안

본 이슈에서는 방향만 제시. 실제 정책 결정은 별도 협의가 필요함.

가능한 방향 (단독 채택 또는 조합):

- 옵션 A. 백그라운드 keep-alive 사이클에 토큰 갱신을 끼워 넣기 (예: 5분마다 access token 유효성 확인 + 만료 임박 시 reissue 선제 호출)
- 옵션 B. 포그라운드 복귀(resume) 시점에 첫 API 호출 전 토큰 유효성 체크 + 필요 시 proactive reissue
- 옵션 C. 강제 로그아웃이 불가피한 경우, 게임 진행 중이었음을 감지해 재로그인 후 진행 중 게임으로 복귀할 수 있는 deep return 흐름 추가
- 옵션 D. 클라이언트 측 JWT payload decode로 만료 시각을 미리 알고 있도록 (현재 부재)
- 옵션 E. 백엔드 측 refresh token 수명 정책 조정 가능 여부 협의

게임 중 강제 로그아웃은 사용자 경험상 가장 치명적이므로 옵션 B(C 조합)가 우선순위가 가장 높을 가능성이 큼.

## ⚙️ 작업 내용

- 백엔드와 access/refresh token 수명 정책 정합 협의
- 클라이언트 토큰 만료 시각 판단 방식 결정 (JWT decode vs 서버 응답 의존 유지)
- keep-alive 또는 resume 훅에 어디서 토큰 갱신을 트리거할지 결정
- 게임 진행 중 강제 로그아웃 시 복귀 UX 정의
- 회귀 방지를 위한 시나리오 정의 (백그라운드 1분 / 30분 / 1시간 / 1일)

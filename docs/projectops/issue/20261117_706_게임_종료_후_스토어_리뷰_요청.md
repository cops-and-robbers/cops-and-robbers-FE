## 🔥 구현 기능

게임이 **정상적으로 끝나고 이겼을 때**, 스토어 기본 리뷰 창(`requestReview()`)을 한 번 띄운다. 별점 화면은 직접 만들지 않는다.

| 항목 | 정한 것 |
|---|---|
| 방식 | `in_app_review` 패키지의 `requestReview()`. Android는 Play 리뷰 창, iOS는 시스템 별점 창 |
| 시점 | 결과 다이얼로그에서 **"홈으로"나 "한 번 더"를 누른 직후**. 방장 여부는 따지지 않는다 |
| 광고 | 리뷰를 요청하는 판은 **전면 광고를 건너뛴다**. 로드된 광고는 버려지지 않고 다음 판에 쓴다 |
| 조건 | 이긴 판 + 정상 종료한 판 2판째 이상 + 마지막 요청 후 120일 경과 |
| 제외 | 중도 퇴장·몰수패, 이벤트 게임, 승패를 알 수 없는 판(`winnerTeam == null`), 앱을 켤 때 |
| 측정 | 요청을 보낸 횟수만 Analytics로 남긴다 (창이 떴는지는 앱이 알 수 없다) |

<br>

## 📝 현재 문제점

- 2026-11-17 회의에서 게임이 끝났을 때 별점·리뷰를 받을 방법을 알아보기로 했다 (의민 담당).
- 앱에는 스토어 주소(`lib/core/constants/app_urls.dart`)만 있고, 리뷰를 요청하는 코드도 패키지도 없다.
- 게임 종료 흐름은 `game_page.dart`의 `_exitGameAfterAd()`가 먼저 화면을 옮기고 그 위에 전면 광고를 덮는다. 광고가 닫힐 때 실행되는 `onComplete`는 비어 있다.

<br>

## 🛠️ 해결 방안 / 제안 기능

### 왜 이 시점인가

- 두 스토어 모두 "만족한 순간"을 권한다. 이긴 판의 결과 직후가 그렇다. 진 직후는 낮은 점수가 나온다는 사례가 있다.
- 광고를 본 뒤에 묻으면 이긴 기분이 식은 뒤가 된다. 그래서 요청하는 판만 광고를 건너뛴다. 한 사람당 약 4개월에 광고 한 번을 덜 보여 주는 셈이다.
- 앱을 켤 때 띄운 사례는 찾지 못했다. 켜는 순간은 방에 들어가려는 사람을 막고, 홈의 진행 중 게임 복구 흐름과도 겹친다.
- 앱을 그냥 끄면 그 판은 넘어간다. 판 수는 결과 다이얼로그가 뜰 때 올려 저장하므로, 다음에 이긴 판에서 같은 조건으로 다시 시도한다.

### 값마다의 근거

| 값 | 근거 | 근거의 종류 |
|---|---|---|
| 스토어 기본 창(`requestReview()`)만 쓴다 | Google: "앱이 마음에 드세요?" 같은 질문을 리뷰 전에 하면 안 되고, 카드를 수정하면 안 된다 ([In-App Review API](https://developer.android.com/guide/playcore/in-app-review)). Apple: 직접 만든 리뷰 창 금지 ([심사 지침 5.6.1](https://developer.apple.com/app-store/review/guidelines/), 요약본으로 확인) | 공식 규정 |
| 간격 120일 | Apple: "365일에 3번까지" ([평점·리뷰 안내](https://developer.apple.com/app-store/ratings-and-reviews/)). 365 ÷ 3 ≈ 122일이라 120일로 둔다. Google: 한 달 안에 다시 부르면 안 뜰 수 있다 ([In-App Review API](https://developer.android.com/guide/playcore/in-app-review)). 120일은 이 조건도 넘긴다 | 공식 수치에서 계산 |
| 2판째 이상 | Google: "유용한 의견을 줄 만큼 충분히 써 본 뒤" 요청 ([In-App Review API](https://developer.android.com/guide/playcore/in-app-review)). Water Sort Puzzle은 게임을 두 번째로 켰을 때부터 띄워 평점 4.8을 받았다 ([Appodeal 사례](https://appodeal.com/success-stories/12x-organic-users-optimizing-rating-prompt-water-sort-puzzle-success/)) | 공식 원칙 + 사례 유추. "2"라는 숫자를 직접 정한 문서는 없다 |
| 이긴 판만 | Apple: "가장 만족할 때, 완료한 동작·레벨·과제 뒤" ([평점·리뷰 안내](https://developer.apple.com/app-store/ratings-and-reviews/)). CyberAgent는 만족이 높은 순간 직후에 띄웠다 ([Google Play 사례](https://google.play/business/case-studies/cyberagent/)). Overwatch 판 평가는 진 판에 낮은 점수가 몰렸다 ([Dot Esports](https://dotesports.com/?p=14646), 검색 요약만) | 공식 원칙 + 사례 |
| 버튼을 누른 직후, 그 판은 광고를 건너뛴다 | Apple: "활동을 끊지 말 것" ([평점·리뷰 안내](https://developer.apple.com/app-store/ratings-and-reviews/)). 사례들은 모두 결과 직후에 띄웠다. 우리 앱은 결과와 리뷰 창 사이에 전면 광고가 낀다 (`game_page.dart`의 `_exitGameAfterAd`) | 사례 + 우리 코드. 광고를 건너뛰라는 문서는 없고 팀 판단이다 |
| 앱이 간격을 직접 막는다 | 이길 때마다 띄운 게임은 반감을 샀다 ([505 Games 포럼](https://forums.505go.com/t/rating-prompt-has-no-option-to-stop-bothering-me-devs-aware/38356), 검색 요약만). 두 스토어 모두 창이 떴는지 앱에 알려 주지 않는다 | 사례 + 공식 문서 |
| 앱을 켤 때는 띄우지 않는다 | 그런 사례를 찾지 못했다. Apple의 "활동을 끊지 말 것"에도 걸린다 | 사례 없음 + 공식 원칙 |

> [!IMPORTANT]
> 간격이 30일이면 iOS에서는 1년에 12번 요청해 9번은 창이 안 뜬다. 앱은 창이 떴는지 알 수 없어서, 그 판은 광고만 건너뛴 채 아무것도 안 뜬다. 그래서 120일이다.

### 스토어 규정

> [!WARNING]
> - 리뷰 창을 띄우기 전에 "앱이 마음에 드세요?", "별 5개 주실래요?" 같은 질문을 하면 안 된다 (Google 공식 문서).
> - 직접 만든 리뷰 창은 금지다 (Apple 심사 지침 5.6.1, 요약본으로만 확인).
> - 버튼으로 `requestReview()`를 부르지 않는다. 설정에 "앱 평가하기" 버튼을 두려면 `openStoreListing()`으로 스토어 페이지를 연다 (횟수 제한 없음, 이번 범위 밖).
> - 리뷰를 쓰면 보상을 주는 것은 두 스토어 모두 금지다.

## ❓ 확인 필요

| 항목 | 상태 |
|---|---|
| "2판째 이상" | 공식 문서에 숫자가 없어 사례에서 유추한 값이다. 출시 뒤 리뷰 수를 보고 조정할 수 있게 상수로 둔다 |
| 진영별 승률 | 확인하지 않았다. 이긴 판만 대상이라 한쪽 진영이 거의 못 이기면 그 진영은 요청을 못 받는다 |
| 건너뛴 전면 광고의 유효 시간 | 확인하지 않았다. 다음 판까지 남는지 코드로 확인 필요 |
| `in_app_review` 2.0.12 설치·빌드 | 버전 범위(Dart `>=2.12 <4.0`)만 확인, 실제 빌드는 안 해 봤다 |
| Apple 문서 원문 | 문서 페이지가 비어 열리지 않았다. TestFlight 동작과 365일 3회는 패키지 README와 Apple 평가 안내 페이지로 확인 |

## 🚧 작업목록

- [ ] `in_app_review` 의존성 추가
- [ ] 결과 다이얼로그가 뜰 때 정상 종료 판 수 증가·저장 (`shared_preferences`)

- [ ] "홈으로"·"한 번 더" 경로에서 조건을 만족하면 전면 광고 대신 `requestReview()` 호출
- [ ] 요청 횟수 Analytics 이벤트
- [ ] 단위 테스트: 조건 판정 (이김/짐/승패 미상/이벤트/중도 퇴장, 1판째, 119일·120일 경계)
- [ ] 확인: iOS 시뮬레이터(개발 빌드), Android Play 내부 테스트 트랙

> [!TIP]
> 실제 리뷰 제출은 출시 전에 확인할 수 없다. iOS는 TestFlight에서 아무것도 하지 않고, 개발 빌드에서는 제출 버튼이 눌리지 않는다. Android는 Play 내부 테스트 트랙으로 설치한 계정이 아직 리뷰를 남기지 않았어야 뜬다 (내부 앱 공유로 설치하면 제출 불가). 효과는 출시 뒤 어드민 리뷰 받은편지함(웹 #255)의 리뷰 수와 평점으로 본다.

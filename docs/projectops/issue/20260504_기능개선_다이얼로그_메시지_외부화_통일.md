## 본문

## 📝 현재 문제점

### 메시지 관리 측면

- 사용자에게 노출되는 메시지 일부는 외부 JSON으로 분리되어 있으나, 대부분은 코드에 하드코딩되어 있어 관리 위치가 이원화되어 있음
- 코드베이스 전수 조사 결과 외부화 필요 메시지가 약 110건 이상 존재함
- 마케팅/기획에서 문구 수정 요청이 올 때마다 코드 수정 + 리뷰 + 빌드가 필요해 대응 속도가 느림
- 동일한 의미의 메시지(예: "이미 참가 중인 게임이 있습니다.")가 여러 파일에 중복 작성되어 있어 변경 시 누락 위험이 있음

### 국제화 측면

- 현재 모든 사용자 노출 텍스트가 한국어로 하드코딩되어 있어 해외 사용자(영어권 등) 대응 불가
- 시스템 로캘이 영어인 단말에서도 한국어로만 표시되어 UX 저하
- 추후 i18n을 별도 프로젝트로 도입할 경우, 코드 전수 수정이 두 번 발생함 (외부화 → 국제화) → **한 번에 진행하여 작업량과 회귀 위험 최소화**

### 언어 전환 기능 측면

- 사용자가 앱 내에서 언어를 직접 선택할 수 있는 수단이 없음
- 시스템 언어와 다른 언어로 앱을 사용하고 싶은 사용자(예: 한국어 학습자, 다국어 사용자) 대응 불가
- 언어 변경 시 앱 재시작 없이 즉시 반영되어야 함

## 🛠️ 해결 방안

### A. 국제화 기반 기술: `flutter_localizations` + `intl` 채택

- **ARB 파일 작성**: `lib/l10n/app_ko.arb`, `app_en.arb`, `app_ja.arb`
- **코드 생성**: `flutter gen-l10n` → `AppLocalizations` 클래스 자동 생성
- **사용 예시**: `AppLocalizations.of(context)!.welcomeMessage`
- **MaterialApp 연동**: `localizationsDelegates`, `supportedLocales` 등록

**선정 사유** (옵션 1: 자체 JSON 로더 확장 / 옵션 3: `easy_localization`과 비교 후 결정)

- 약 110+ 건 × 3개 언어 = **330건 이상**을 문자열 키로 관리하면 오타 시 런타임 에러 위험 큼 → **컴파일 타임 타입 안전성 확보** 우선
- ARB는 번역 도구(Crowdin, Lokalise 등) 표준 포맷 → **번역가/외부 협업 시 유리**
- Material/Cupertino 위젯의 일본어 표시 자동 처리 (DatePicker, 다이얼로그 버튼 등)
- ICU MessageFormat으로 영어 복수형(`{count, plural, =1{thief} other{thieves}}`) 처리 내장
- Flutter 공식 패턴이라 SDK 업그레이드/장기 유지보수 안정성 높음
- 기존 JSON 파일이 2개뿐이라 마이그레이션 부담 적음 — 기존 패턴 일관성보다 새 표준 도입 가치가 큼

### B. 언어 전환 기능

- **Locale 상태 관리**: `@riverpod` 기반 `LocaleNotifier` 도입 (`keepAlive: true`)
- **저장소**: `SharedPreferences`에 사용자 선택 언어 코드 저장
- **앱 시작 시 우선순위**:
  1. 사용자가 명시적으로 선택한 언어 (`SharedPreferences`)
  2. 시스템 로캘 (`PlatformDispatcher.instance.locale`)
  3. 기본값 (`ko`)
- **언어 전환 UI**: `settings_page.dart`에 "언어" 항목 추가 → 모달/페이지로 선택지 노출
- **즉시 반영**: `MaterialApp`의 `locale` 파라미터를 Provider에서 watch하여 rebuild
- **테마와 연계**: `roleThemeProvider`와 마찬가지로 prop drilling 없이 최상단에서 watch

### C. 메시지 키 설계

- **ARB 파일 단위**: 도메인별 분리 대신 단일 `app_{locale}.arb` 사용 (`flutter gen-l10n` 표준)
  - 도메인별 분리는 키 prefix로 처리 (예: `dialogSessionBatteryOptimizationTitle`)
- **키 네이밍**: camelCase + 도메인 prefix (예: `dialogSessionBatteryOptimizationTitle`, `snackbarErrorNetworkOffline`)
- **동적 보간**: ARB placeholder 사용 (예: `"greeting": "{nickname}님 환영합니다"` + `"@greeting": { "placeholders": { "nickname": { "type": "String" } } }`)
- **복수형 처리**: ICU MessageFormat (예: `{count, plural, =1{1명} other{{count}명}}`)
- **누락 키 정책**: `untranslated-messages-file` 옵션으로 빌드 시 누락된 번역 키 추적

## 🪶 문구 컨벤션 (이전 시 일괄 적용)

- 메시지 마지막 문장 끝에 마침표(`.`)를 찍지 않는다. `assets/messages/location_permission_messages.json`을 정본으로 한다
  - 예: "위치 서비스가 꺼져 있습니다", "기기 설정에서 위치 서비스를 켜주세요"
- 문장 중간(여러 문장이 이어질 때 사이의 마침표)은 의미상 필요하면 사용해도 무방
- 물음표(`?`), 느낌표(`!`)는 별개 — 의미상 필요하면 사용
- 영어 번역 시 sentence case 기본 (Title Case는 버튼/제목 등 일부만)
- 현재 하드코딩된 문구 중 끝에 마침표가 붙어 있는 항목은 외부화 시점에 일괄 정리

## ⚠️ 리스크 / 고려사항

- **번역 품질**: 게임 도메인 용어(체포, 탈옥, 도둑, 경찰 등) en/ja 번역 일관성 — 용어집(glossary) 사전 작성 필수
- **레이아웃 깨짐**:
  - 영어는 한국어 대비 1.3~1.5배 길어져 버튼/타이틀 오버플로우 위험
  - 일본어는 한자 혼용으로 줄바꿈 위치가 한국어와 달라 가독성 점검 필요
- **폰트 호환성**:
  - Pretendard는 ko/en/ja 모두 지원 — 무난
  - Moneygraphy(도둑 전용)는 한글 전용 디자인 가능성 → 영문/일본어 fallback 폰트 정책 결정
- **ARB 키 누락 시 동작**: `flutter gen-l10n`은 기본적으로 누락 키를 허용 → CI에서 누락 키 검출 스크립트 추가 검토
- **STOMP/서버 메시지**: 백엔드에서 내려오는 에러 메시지(`detail` 필드 등)는 서버 측 i18n 협의 필요 — **본 이슈 범위 외**로 별도 분리
- **푸시 알림**: FCM payload의 메시지도 i18n 대상 — **본 이슈 범위 외**로 별도 분리 (서버 작업 동반)
- **작업량**: 약 110+ 건 메시지 × 3개 언어 = **330+ 번역 항목**, LLM 일괄 번역 활용해도 도메인 검수 시간 확보 필요
- **빌드 단계 추가**: `flutter gen-l10n` 자동 실행 확인 (`pub get` 시 트리거됨), CI/CD 빌드 시간 영향은 미미

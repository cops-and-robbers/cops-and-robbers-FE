## 0. 역할 분담 & 백엔드 액션 아이템

이벤트 모드는 **코드량·체감 동작의 ~8할이 프론트엔드** 몫입니다.
단, 아래 백엔드 코어가 없으면 프론트가 아무리 잘 짜도 동작하지 않으니 **명시적으로 확정** 부탁드립니다.

**백엔드가 반드시 해야 하는 것 (프론트가 대체 불가):**

1. 🔧 **이벤트 방 생성 경로** — 운영진이 `isEventGame=true` 방을 만드는 경로. **현재 스펙에 누락** (§1-A 참고)
2. 🔧 **`join` 응답에 `isEventGame`** 필드 추가 (§1)
3. ❓ **엔진 룰 분기** — 체포 시 `JAILED` 안 함 / `remainingThieves` 안 깎음 / `ALL_ARRESTED`·`POLICE_FORFEITED` 종료 안 함 / FCM 없음 (§3, §4)

**프론트가 자체 처리 (백엔드 작업 없음):**

- 체포 수 카운트 & 재체포 방지 → **로컬 + 로컬 영속화** (백엔드 미사용)
- 로비 스킵 라우팅 / 중간 입장 부트스트랩 / 도둑 ALIVE UI / 결과 표시

## 1. API 변경 사항

### POST `/api/games/join`

**Request** (원안 유지)

```json
{
  "inviteCode": "ABC123"
}
```

**Response**

```json
{
  "gameId": 1,
  "participantId": 42,
  "isEventGame": true
}
```

- ✅ 엔드포인트 경로·요청 바디는 현재 프론트 구현과 일치 (`POST /api/games/join`).
- 🔧 `isEventGame`: **응답 신규 필드.** `true`이면 로비 화면을 스킵하고 인게임 화면으로 이동.
  - 현재 `api-docs.json`의 `GameJoinResponse`에는 `gameId`, `participantId`만 있음 → 필드 추가 필요.

### 🔧 [누락] 1-A. 이벤트 방 *생성* 경로

`join`은 "참가(소비)"만 다루고, **운영진이 이벤트 방을 *생성*하는 경로가 스펙에 없습니다.**
어딘가에서 방이 `isEventGame=true`로 마킹되어야 위 `join` 응답이 `true`를 내려줄 수 있습니다.

- ❓ 게임 생성 API(`POST /api/games` 등)에 "이벤트 게임 여부" 설정이 추가되는지?
- ❓ 추가된다면 요청 필드명/기본값은? (예: `isEventGame: false` 기본)

이 부분 확정 후 프론트도 (필요 시) 생성 UI를 붙입니다.

## 2. QR 입장 플로우

🔧 **수정:** 원안 플로우의 요청 바디에 `isEventGame: true`가 포함돼 있었으나,
클라이언트는 `join` **전에는** 이벤트 게임 여부를 알 수 없으므로 **요청에서 제거**합니다. (`isEventGame`은 응답 전용)

```
QR 스캔
  → POST /api/games/join { inviteCode }          // isEventGame 보내지 않음
  → 응답 isEventGame == true
       → 로비/대기실 스킵
       → 🖥️ 부트스트랩 조회 (아래)
       → WebSocket 구독 시작 (/subscribe/game/{gameId}/system 등)
       → 인게임 화면으로 바로 이동
```

### 🖥️ 중간 입장 부트스트랩 (프론트 처리, 백엔드 추가 개발 불필요)

로비를 스킵한 중간 입장자는 로비 STOMP에서 발생하는 `SETTINGS_UPDATED` / `AREA_UPDATED` / `GAME_START`를 **받지 못합니다.**
따라서 인게임 진입 시 아래 **기존 API**로 상태를 채웁니다 (모두 이미 존재):

| 데이터 | 엔드포인트 |
| --- | --- |
| 게임 설정 / `gameStartTime` | `GET /api/games/{gameId}` |
| 게임 영역(운동장/감옥) | `GET /api/games/{gameId}/area` |
| 참가자 상태 + 기존 공개된 도둑 위치 | `GET /api/games/{gameId}/state` |

> ❓ 확인만: 위 3개가 **중간 입장 직후(IN_PROGRESS)에도** 정상 응답하는지. (`/state`는 IN_PROGRESS 전용이라 OK로 보임)

### QR 입장 시 발생 가능한 에러 (원안 유지)

| 에러 코드               | 상황                            |
| ----------------------- | ------------------------------- |
| `ALREADY_PARTICIPATING` | 이미 다른 게임에 참여 중        |
| `INVALID_INVITE_CODE`   | 잘못된 QR 또는 만료된 초대 코드 |

- ✅ 두 에러 모두 프론트에서 이미 처리 중.

## 3. 이벤트 게임 중 체포(`ARREST`) 처리

**WebSocket `ARREST` 페이로드 구조는 동일하며 값만 달라짐** (원안 유지)

```json
{
  "type": "ARREST",
  "data": {
    "police": { "participantId": 10, "nickname": "경찰A", "status": "ALIVE" },
    "robber": { "participantId": 20, "nickname": "도둑B(운영진)", "status": "ALIVE" },
    "remainingThieves": 3
  }
}
```

- ✅ 도둑(운영진)은 체포 후에도 `ALIVE` 유지 (`JAILED`로 변경 X) — **백엔드 엔진 분기 필요** (§0-3)
- ✅ `remainingThieves`는 줄어들지 않음 — **백엔드 엔진 분기 필요** (§0-3)
- ✅ FCM 푸시 없음 (`ARREST` WebSocket 브로드캐스트만) — **백엔드 엔진 분기 필요** (§0-3)
- ✅ **UI 트리거는 `type: ARREST` 수신 자체를 기준으로 함.**
  - 🖥️ 프론트는 이미 `robber.status`가 아니라 이벤트 수신 기준으로 동작하므로 추가 변경 불필요.

### 체포 카운트 — 🖥️ 로컬 처리 (백엔드 미사용)

✅ **결정: 체포 수는 프론트 로컬에서만 카운트하고 백엔드로 보내지 않음.**

```
ARREST 이벤트 수신 시:
  if (data.police.participantId == 내 participantId) {
    내 체포 카운트 +1
  }
```

🖥️ **로컬 영속화 필수.** 단순 메모리 카운트는 백그라운드 복귀/스플래시 재진입 시
재동기화(`GET /state`가 `status=ALIVE`만 내려줌)로 로컬 집합이 비워져 **카운트가 리셋**됩니다.
→ `shared_preferences`에 `gameId`별로 "잡은 도둑 목록 + 카운트"를 저장해 재접속에도 유지.

> 참고(사실관계): **같은 폰** 안에서의 재접속/재실행은 영속화로 커버되지만, **폰을 교체하면 리셋**됩니다.
> 행사 시나리오(1인 1폰)에선 무관. 정확한 집계가 운영상 중요해지면 그때만 서버 보관을 재논의.

### 재체포 방지 — 🖥️ 로컬 처리 (기존 게임과 동일)

```
ARREST 이벤트 수신 시:
  if (data.police.participantId == 내 participantId) {
    "내가 잡은 도둑" 목록(영속화 집합)에 data.robber.participantId 추가
  }

체포 버튼 렌더링 시:
  if ("내가 잡은 도둑" 목록에 해당 participantId 포함) {
    체포 버튼 비활성화
  }
```

- 위 "체포 카운트"의 영속화 집합을 공유하여 재접속 후에도 재체포 방지가 유지됨.
- 작업 가정: **기존 게임과 동일하게 재체포 차단 유지** (경찰은 각 운영진 1회씩).
  운영진 수가 적어 "다 잡으면 끝"이 너무 빠르면 **추후 재체포 허용으로 전환** 가능 — 그 경우만 재논의.

## 4. 게임 종료 조건 차이

| 종료 조건          | 일반 게임 | 이벤트 게임    |
| ------------------ | --------- | -------------- |
| `ALL_ARRESTED`     | 발생 O    | **발생 안 함** |
| `TIME_OVER`        | 발생 O    | 발생 O         |
| `ROBBER_FORFEITED` | 발생 O    | 발생 O         |
| `POLICE_FORFEITED` | 발생 O    | **발생 안 함** |

`GAME_OVER` 이벤트 구조와 페이로드는 기존과 동일. `reason` 값만 달라짐.

- ❓ **백엔드 확인:** `ROBBER_FORFEITED` / `POLICE_FORFEITED`의 의미·발생 조건.
  - 운영진 = 도둑인데 "도둑 기권(`ROBBER_FORFEITED`)"은 어떤 상태인지? (운영진 전원 이탈?)
  - 경찰(사용자) 전원이 나가도 게임이 유지되어 `POLICE_FORFEITED`가 안 나는 것인지?
- 🖥️ **`winnerTeam` 해석:** 행사 체험이라 팀 승패 의미가 약함 → 결과 화면은 `winnerTeam` 대신
  **내 로컬 카운트("운영진 N명 검거")**를 표시. `GAME_OVER` 페이로드는 기존 그대로 보내도 무방.
- 🖥️ **프론트 작업:** 현재 `GameResultReason`에 `ALL_ARRESTED`/`TIME_OVER`만 정의됨 → `*_FORFEITED` 상수 추가 필요.

## 5. 중간 입장 시 참가자 초기 상태 (원안 유지)

QR로 중간 입장한 경찰의 초기 상태는 경찰 이동 시작 시간 기준으로 결정.

- 경찰 이동 시작 시간이 지난 경우: `ALIVE`
- 경찰 이동 시작 시간이 지나지 않은 경우: `POLICE_WAITING`

이벤트 게임은 일반적으로 `policeWaitMinutes=0`이므로 대부분 `ALIVE`로 입장.

- ✅ 프론트 `canPoliceArrest()`가 이미 처리. `policeWaitMinutes` / `gameStartTime` 기준으로 체포 가능 여부 판단.

## 6. 체포된 도둑(운영진) ALIVE UI — ✅ 결정 (원안 미결 → 확정)

> 원안 "확인 필요"였던 "체포 후에도 도둑 상태가 ALIVE인데 UI를 어떻게 처리할지"를 아래와 같이 확정.

- **운영진(도둑) 본인 화면:** 잡혀도 **감옥 잠금 오버레이·탈옥 버튼을 숨기고** 계속 플레이.
  - (일반 게임의 `arrest_lock_overlay` / 탈옥 플로우를 이벤트 모드에선 비활성)
- **경찰 화면:** 체포 성공 시 피드백(토스트/애니메이션) 표시. 재체포 방지 유지에 따라 잡은 운영진은 "검거됨" 표시.
- 🖥️ 모두 `isEventGame` 분기로 프론트에서 처리 (백엔드 작업 없음).

> 핵심: 백엔드가 `status=ALIVE`를 내려줘도 프론트는 **로컬 집합으로 "갇힘" UI를 그리므로**,
> 이벤트 모드에서 감옥/탈옥 UI를 끄는 건 백엔드가 대신해줄 수 없는 **순수 프론트 작업**임.

## 본문

## 🔨 리팩토링 기능

API 실패 응답값이 한글 문구와 매직 스트링으로 내려오고 있어, 프론트엔드에서 실패 케이스를 분기하거나 국제화(i18n) 처리하기 어렵습니다. 응답에 머신이 식별할 수 있는 SCREAMING_SNAKE_CASE 형태의 에러코드를 추가하고, 에러 문구 체계를 표준화해주세요.

## 📖 리팩토링 내용

현재 프론트는 다국어(ko/en/ja)를 지원해야 하는데, 실패 응답이 한글 고정 문구로 내려와서 다음 문제가 발생합니다.

- 응답 문구가 한글로 하드코딩되어 있어 영어/일본어 환경에서 그대로 노출됨
- 에러를 구분할 식별자가 없어, 한글 문구 텍스트 자체를 비교해 분기해야 함 (매직 스트링 의존)
- 백엔드 문구가 한 글자라도 바뀌면 프론트 분기 로직이 깨짐

요청 사항은 다음과 같습니다.

- 모든 실패 응답에 SCREAMING_SNAKE_CASE 형태의 고유 에러코드 필드를 포함 (예: `INVALID_INVITE_CODE`, `GAME_ALREADY_STARTED`, `PARTICIPANT_NOT_FOUND`)
- 에러코드는 변하지 않는 식별자로 사용하고, 프론트는 이 코드를 기준으로 분기 및 국제화 메시지 매핑
- 응답 문구(한글)는 기본 fallback 용도로만 사용 → 실제 사용자 노출 문구는 프론트가 에러코드로 i18n 처리
- 기존 RFC 7807(Problem Details) 구조를 유지하면서 에러코드 식별자만 추가하는 방향 선호
- 에러코드 목록을 문서(또는 Enum)로 공유하여 프론트와 싱크 유지

## 📦 응답 구조 예시

### AS-IS (현재)

식별 가능한 코드 없이 한글 문구만 내려옴 → 프론트는 `detail` 텍스트를 직접 비교해야 함

```json
{
  "title": "잘못된 초대 코드",
  "status": 400,
  "detail": "유효하지 않은 초대 코드입니다.",
  "instance": "/api/games/1/participants"
}
```

### TO-BE (제안)

RFC 7807 구조를 유지한 채 `errorCode` 필드만 추가 → 프론트는 `errorCode`로 분기 + i18n 매핑, `detail`은 fallback

```json
{
  "errorCode": "INVALID_INVITE_CODE",
  "title": "잘못된 초대 코드",
  "status": 400,
  "detail": "유효하지 않은 초대 코드입니다.",
  "instance": "/api/games/1/participants"
}
```

### STOMP 에러 응답 (동일 체계 적용 시)

```json
{
  "errorCode": "SUBSCRIBE_FORBIDDEN",
  "title": "구독 권한 없음",
  "status": 401,
  "detail": "해당 팀 전용 채널을 구독할 권한이 없습니다.",
  "instance": "STOMP"
}
```

> 필드명(`errorCode`)과 코드 네이밍은 예시이며, 백엔드 컨벤션에 맞게 협의 후 확정하면 됩니다. 핵심은 "변하지 않는 머신 식별자"가 응답에 포함되는 것입니다.

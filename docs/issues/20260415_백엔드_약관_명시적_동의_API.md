## 🔥 구현 기능

현재 앱은 가입 시점에 이용약관·개인정보처리방침을 묵시적으로 동의한 것으로 처리하고 있다.
앞으로는 이용약관, 개인정보처리방침, 위치정보 이용약관 3종을 사용자가 명시적으로 체크해 동의하도록 변경한다.

- 앱 정식 출시 전이므로 기존 DB는 초기화 가능 (마이그레이션 고려 불필요)
- `/api/auth/login` 요청 스펙은 변경 없음 (단일 책임 유지)
- 로그인 응답에 `requiresAgreement` 플래그 1개만 추가
- 약관 동의 수집은 신규 엔드포인트 `/api/auth/agreements`에서만 담당

### 동의 받을 약관 목록

| type | 이름 | 필수 여부 |
| --- | --- | --- |
| `TERMS_OF_SERVICE` | 이용약관 | 필수 |
| `PRIVACY_POLICY` | 개인정보처리방침 | 필수 |
| `LOCATION_TERMS` | 위치정보 이용약관 | 필수 |
| `MARKETING` | 마케팅 정보 수신 | 선택 |

## 📘 API 스펙

### 1. `POST /api/auth/login` — 응답 스키마 변경

`LoginResponse`에 `requiresAgreement` 필드 추가. 요청 스펙(`LoginRequest`)은 변경 없음.

#### `LoginResponse` (변경 후)

```json
{
  "userId": 2,
  "nickname": "집요한괴도4053",
  "tokens": {
    "accessToken": "eyJhbGciOiJIUzUxMiJ9...",
    "refreshToken": "eyJhbGciOiJIUzUxMiJ9..."
  },
  "isNewUser": true,
  "requiresAgreement": true
}
```

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `requiresAgreement` | boolean | 필수 약관 중 하나라도 동의하지 않은 경우 `true`. 신규 회원은 항상 `true`. 모든 필수 약관 동의 완료 시 `false`. |

#### 동작 규칙

- `isNewUser = true`인 신규 가입 응답(201)에서는 항상 `requiresAgreement = true`
- `isNewUser = false`인 기존 회원 응답(200)에서도, 필수 약관 중 미동의 항목이 있으면 `requiresAgreement = true`
- 에러 응답(400/401/500)은 기존 스펙 그대로 유지 (변경 없음)

### 2. `POST /api/auth/agreements` — 신규 엔드포인트

약관 동의 정보를 저장한다. 로그인 후 `requiresAgreement = true`인 경우 프론트가 호출한다.

#### 기본 정보

| 항목 | 값 |
| --- | --- |
| Method | `POST` |
| Path | `/api/auth/agreements` |
| Tags | `Auth` |
| 인증 | **필수** (`Authorization: Bearer {accessToken}`) |
| Content-Type | `application/json` |

#### Request Body — `AgreementRequest`

```json
{
  "termsOfService": true,
  "privacyPolicy": true,
  "locationTerms": true,
  "marketing": false
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `termsOfService` | boolean | Y | 이용약관 동의 여부 (필수 약관, `true`만 허용) |
| `privacyPolicy` | boolean | Y | 개인정보처리방침 동의 여부 (필수 약관, `true`만 허용) |
| `locationTerms` | boolean | Y | 위치정보 이용약관 동의 여부 (필수 약관, `true`만 허용) |
| `marketing` | boolean | Y | 마케팅 정보 수신 동의 여부 (선택 약관, `true`/`false` 모두 허용) |

#### Response

| HTTP | 설명 |
| --- | --- |
| `204 No Content` | 약관 동의 저장 성공. 응답 본문 없음. |

##### 에러 응답 (`ErrorResponse`)

기존 RFC 7807 스타일 유지. `instance` 필드는 `/api/auth/agreements`.

**`400` — 유효하지 않은 입력값 (필수 약관 미동의)**
```json
{
  "title": "유효하지 않은 입력값",
  "status": 400,
  "detail": "필수 약관에 모두 동의해야 합니다.",
  "instance": "/api/auth/agreements"
}
```

**`400` — 유효하지 않은 입력값 (필드 누락 등)**
```json
{
  "title": "유효하지 않은 입력값",
  "status": 400,
  "detail": "입력값이 유효성 검사를 통과하지 못했습니다.",
  "instance": "/api/auth/agreements"
}
```

**`401` — 인증 만료**
```json
{
  "title": "인증 만료",
  "status": 401,
  "detail": "인증정보가 만료되었습니다.",
  "instance": "/api/auth/agreements"
}
```

**`401` — 존재하지 않는 회원**
```json
{
  "title": "존재하지 않는 회원",
  "status": 401,
  "detail": "해당 유저을 찾을 수 없습니다.",
  "instance": "/api/auth/agreements"
}
```

**`409` — 이미 동의 완료된 사용자 재요청 (선택)**

프론트 중복 요청 방어용. 서버 정책에 따라 `409` 대신 `204`로 멱등 처리해도 무방.
```json
{
  "title": "이미 동의 완료",
  "status": 409,
  "detail": "이미 필수 약관 동의가 완료된 사용자입니다.",
  "instance": "/api/auth/agreements"
}
```

**`500` — 알 수 없는 오류**
```json
{
  "title": "알 수 없는 오류",
  "status": 500,
  "detail": "서버 내부에 알 수 없는 오류가 발생했습니다. 관리자에게 문의 하세요.",
  "instance": "/api/auth/agreements"
}
```

### 3. 미동의 사용자 보호 API 접근 정책 (합의 필요)

`requiresAgreement = true` 상태의 사용자가 약관 동의를 건너뛰고 다른 보호 API를 호출했을 때의 처리 방식. 두 가지 중 선택 필요.

**옵션 A — 서버 필터 차단 (권장)**
- `/api/auth/agreements`, `/api/auth/logout`, `/api/auth/reissue`를 제외한 모든 보호 API에 대해 `403` 반환
- 에러 응답 예시
  ```json
  {
    "title": "약관 동의 필요",
    "status": 403,
    "detail": "필수 약관에 동의해야 서비스를 이용할 수 있습니다.",
    "instance": "/api/games/1"
  }
  ```

**옵션 B — 프론트 라우팅으로만 차단**
- 서버는 아무것도 하지 않음
- 프론트가 `requiresAgreement` 값으로 약관 동의 화면 이외 진입을 막음
- 장점: 구현 단순. 단점: API 직접 호출 우회 가능

## 🗄️ DB 스키마 제안

약관 버전 관리까지 고려한 정규화 구조. 정식 출시 전이라 기존 데이터는 초기화 가능.

### `term` (약관 마스터)

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | bigint PK | |
| `type` | varchar(32) | `TERMS_OF_SERVICE` / `PRIVACY_POLICY` / `LOCATION_TERMS` / `MARKETING` |
| `version` | int | 개정 시마다 증가 |
| `required` | boolean | 필수 약관 여부 |
| `published_at` | timestamp | 약관 공표 시각 |
| `content_url` | varchar(255) nullable | 약관 본문 위치 (선택) |

**UNIQUE**: `(type, version)`

### `user_term_agreement` (사용자 동의 이력)

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | bigint PK | |
| `user_id` | bigint FK → `user.id` | |
| `term_id` | bigint FK → `term.id` | |
| `agreed_at` | timestamp | 동의 시각 |

**INDEX**: `(user_id, term_id)`

### 초기 시딩

| type | version | required |
| --- | --- | --- |
| `TERMS_OF_SERVICE` | 1 | true |
| `PRIVACY_POLICY` | 1 | true |
| `LOCATION_TERMS` | 1 | true |
| `MARKETING` | 1 | false |

### `requiresAgreement` 판별 쿼리 (예시)

```sql
-- 해당 유저가 아직 동의하지 않은 필수 약관이 있으면 true
SELECT EXISTS (
  SELECT 1
  FROM term t
  WHERE t.required = true
    AND NOT EXISTS (
      SELECT 1
      FROM user_term_agreement uta
      WHERE uta.user_id = :userId
        AND uta.term_id = t.id
    )
);
```

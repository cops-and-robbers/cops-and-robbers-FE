## Part 1 · 대기실 튜토리얼 팀별 노출 및 재노출 (#278)

### 🔍 문제 분석

| 문제 | 원인 |
|---|---|
| 팀을 바꿔도 튜토리얼이 다시 안 뜸 | `tutorial_waiting_room` 단일 키 하나로 완료 여부 저장 — 경찰/도둑이 같은 키 공유 |
| 팀 변경 카드 안내가 한쪽만 노출됨 | 경찰/도둑은 각각 **반대 팀 첫 슬롯**을 가리키므로 타겟 위젯이 물리적으로 다름. 한 키로 묶으면 한쪽을 본 유저는 반대편을 못 보고 끝남 |
| TEAM_UPDATE 이벤트로 UI와 안내가 어긋남 | 튜토리얼 노출 함수 내부에서 현재 팀 값을 다시 읽어 레이아웃 캐시 시점과 안내 타겟 시점이 불일치할 여지 있음 |
| STOMP race condition | `endOfFrame` 대기 사이에 TEAM_UPDATE가 도착하면 낡은 팀 기준 튜토리얼이 신규 튜토리얼 시작을 막음 |

### 🎯 구현 목표

- 경찰/도둑 완료 상태를 각각 별개 키로 저장
- 팀 최초 확정 + 팀 변경 모두 단일 리스너에서 처리
- 진행 중 튜토리얼 종료 후 새 팀 튜토리얼 즉시 이어서 실행
- 양쪽 팀 모두 완료한 유저는 이후 팀을 오가도 재노출 없음
- 반대 팀 정원이 꽉 차 팀 변경 카드가 렌더링되지 않으면 해당 스텝만 조용히 skip

- **변경 내용**:

  - 리스너 쪽에서도 "컨트롤러 없음 + 플래그만 선점된 stale 상태"를 감지해 플래그만 해제하는 경로 추가
- **이유**: endOfFrame 대기 1프레임 사이에 TEAM_UPDATE 이벤트가 들어오면 listener는 새 팀으로 재트리거하지만, 기존 코드에서는 `_isTutorialShowing` 가드에 막혀 새 튜토리얼이 시작되지 않던 문제

### 🔧 주요 로직 상세

#### `_showTutorialIfNeeded(team)` 흐름

```
1. _isTutorialShowing == true → return (중복 방지)
2. key = waitingRoomByTeam(team), null이면 return
3. 완료 상태 조회 → 이미 완료면 return
4. _isTutorialShowing = true, endOfFrame 대기
5. 대기 사이 팀 변경됐으면 조용히 return (flag 유지, listener가 재트리거)
6. 반대 팀 AddSlotCard currentContext 존재 여부로 팀 변경 카드 스텝 포함 결정
7. AppTutorialStyle.show → onFinish에서 해당 팀 키 markCompleted + flag 해제
```

#### 리스너 쪽 전이 관리

```dart
if (!isInitial && !isChanged) return;
final controller = _tutorialController;
if (controller != null && controller.isShowing) {
  controller.finish();  // 이전 팀 키는 onFinish에서 자동 markCompleted
  _tutorialController = null;
  _isTutorialShowing = false;
} else {
  _isTutorialShowing = false;  // stale flag 해제
}
_showTutorialIfNeeded(nextTeam);
```

**특이사항**:
- `tutorial_coach_mark`의 `finish()`는 `onFinish`를 비동기로 호출할 수 있어, 이전 팀의 `markCompleted`가 새 튜토리얼 시작 이후 실행될 여지 있음. `markCompleted`는 저장만 하므로 UX/기능 오동작은 없음
- 반대 팀 정원이 꽉 차 `AddSlotCard`가 `null`인 경우 해당 스텝을 `targets` 배열 조립 단계에서 제외해 조용히 skip
- 참가자 수 변동으로 팀 섹션 Wrap 높이가 바뀌면 아래쪽 타겟 좌표가 밀림 — `ref.listen(waitingRoomParticipantsProvider)`에서 `controller.refresh()` 호출해 좌표 재계산

## Part 2 · 참가자 목록 정렬 개선

### 🔍 문제 분석

대기실과 게임방 참가자 오버레이에서 `TeamSection` 위젯이 방장만 맨 앞으로 올리고 나머지는 서버 수신 순서 그대로였음. 자신의 카드는 볼드 처리(`isMe`)만 되고 정렬에는 반영되지 않아, 참가자가 많을수록 본인을 찾기 번거로웠다.

### 🎯 구현 목표

- 정렬 순서를 **방장 → 본인 → 나머지(수신 순서 유지)** 로 변경
- 대기실과 게임방 참가자 오버레이 양쪽 모두 일관 반영
- "팀 변경 시 해당 유저가 새 팀 맨 뒤로 밀리는" 기존 동작 유지 (Dart `List.sort` 비안정성 회피)

### ✅ 구현 내용

#### 1. 정렬 헬퍼 함수 추출
- **파일**: `lib/features/session/presentation/widgets/team_section.dart`
- **변경 내용**:
  - `sortParticipantsForDisplay(members, {hostParticipantId, myParticipantId})` top-level 함수 추가
  - `@visibleForTesting` 어노테이션으로 위젯 렌더링 없이 순수 단위 테스트 가능하도록 노출
  - `_buildParticipants()` 내 inline `sort` 제거하고 헬퍼 호출로 교체
- **이유**: 정렬 로직 응집도 확보 + 테스트 용이성

#### 2. 정렬 규칙 구현
- **방식**: `where` 3회 필터링 후 spread 결합 (`[...host, ...me, ...others]`)
- **이유**: Dart `List.sort`는 stable이 보장되지 않아 "나머지" 그룹 내부 순서가 뒤섞일 수 있음. `where`는 원본 순서를 그대로 유지하므로 수신 순서 보존 계약이 명시적으로 고정됨
- **엣지케이스**:
  - 내가 방장인 경우 → 방장 그룹에 이미 포함되므로 me 그룹 조건에서 `p.participantId != hostParticipantId`로 명시 제외 (중복 렌더링 방지)
  - 상대 팀 섹션 → 본인이 없으니 me 그룹 비고, 방장만 맨 앞
  - `hostParticipantId` 또는 `myParticipantId`가 `null` → `p.participantId`가 non-null `int`라 비교가 항상 false로 떨어져 안전

### 🔧 주요 로직 상세

```dart
@visibleForTesting
List<LobbyParticipantInfo> sortParticipantsForDisplay(
  List<LobbyParticipantInfo> members, {
  required int? hostParticipantId,
  required int? myParticipantId,
}) {
  final host = members.where((p) => p.participantId == hostParticipantId);
  final me = members.where(
    (p) =>
        p.participantId == myParticipantId &&
        p.participantId != hostParticipantId,
  );
  final others = members.where(
    (p) =>
        p.participantId != hostParticipantId &&
        p.participantId != myParticipantId,
  );
  return [...host, ...me, ...others];
}
```

**특이사항**:
- `TeamSection`이 대기실(`waiting_room_page.dart`)과 게임방 참가자 오버레이(`participant_overlay.dart`) 양쪽에서 공유되므로 한 곳 변경으로 양쪽 자동 반영
- `myParticipantId`는 각 디바이스의 로그인 사용자 기준이라 유저별 화면에서 자신이 각각 2순위로 보임 (동일 위젯이지만 디바이스별 렌더 결과가 다름)

## 📌 참고사항

### 마이그레이션 영향 (#278)
기존 `waitingRoom` 단일 키로 완료 처리된 사용자는 경찰/도둑 각각 최초 진입 시 한 번씩 다시 노출됨. 이슈 명세의 **의도된 동작**.

### 호스트 플로우 주의 (#278)
`WidgetRef.listen`이 future changes만 구독하는 특성상, 방 생성 호스트처럼 페이지 진입 전에 팀이 확정된 케이스는 `_fetchAndInitParticipants()` 말미 명시 호출로만 커버됨. 향후 팀 확정 경로가 추가되면 해당 지점에도 초기 노출 호출 누락 없는지 검토 필요.

### race 방어 지점 (#278)
`endOfFrame` 대기 + listener 재트리거 + stale flag 해제의 3단 방어가 얽혀 있음. 튜토리얼 로직 수정 시 커밋 `76bc1aa`의 가드 로직을 먼저 읽을 것.

### 정렬 공유 위젯 (Part 2)
`TeamSection`은 대기실과 게임방 참가자 오버레이 양쪽에서 공유되므로, 한쪽에서만 다른 정렬을 원한다면 파라미터 플래그 추가가 필요. 현재는 두 화면 동일 규칙.

# errorCode 기반 실패 응답 분기 및 다국어 메시지 매핑 도입 (#386)

### 📌 작업 개요

백엔드 v2.8.0이 모든 실패 응답에 `errorCode`(SCREAMING_SNAKE_CASE) 필드를 추가함에 따라, 기존에 한국어로 고정된 `detail` 문구를 사용자에게 그대로 노출하던 방식을 **errorCode 기반 i18n(ko/en/ja) 매핑**으로 전환했다.

핵심은 ① 에러 응답 파싱·예외 변환 인프라 정비, ② 60여 개 errorCode + 네트워크/인증 키에 대한 다국어 메시지 추가, ③ 각 Notifier/Page의 에러 표시 로직을 매퍼 기반으로 교체, ④ errorCode 카탈로그 문서화다.

---

### 🎯 구현 목표

- 백엔드 `errorCode`를 단일 진실 공급원으로 삼아 에러를 분기 (한국어 고정 `detail`은 fallback·로그 용도로만 사용)
- 정적 클래스(`DioExceptionHandler`)에서는 `BuildContext` 없이 **키만 결정**, UI 레이어에서 `AppLocalizations`로 변환하는 2단계 구조 유지
- 백엔드 errorCode와 Firebase provider code(소셜 인증)를 안전하게 구분
- 매핑 누락 코드도 공통 문구로 폴백해 신규 백엔드 코드 추가 시에도 깨지지 않도록 보장

---

### ✅ 구현 내용

#### 1. 에러 응답 파싱 모델 확장
- **파일**: `lib/core/network/api_error_response.dart`, `lib/core/network/websocket/stomp_connection.dart`
- **변경 내용**: `ApiErrorResponse`·`StompErrorInfo`에 nullable `errorCode` 필드 추가. `tryParse`가 `errorCode`만 있는 응답도 에러로 인식하도록 판정 조건 보강
- **이유**: HTTP·STOMP 양쪽의 v2.8.0+ 응답을 호환하면서, 구버전(errorCode 없는) 응답도 그대로 처리

#### 2. AppException.code 의미 명확화
- **파일**: `lib/core/errors/app_exception.dart`
- **변경 내용**: `code` 필드 주석을 정비해 "서버 발 errorCode(SCREAMING_SNAKE)" vs "Firebase/소셜 provider code(kebab-case)"가 경로별로 다른 의미를 가짐을 명시
- **이유**: 같은 `code` 필드를 두 흐름이 공유하므로, 사용자 노출 변환 시 가드 로직의 전제를 코드에 박아둠

#### 3. DioExceptionHandler — errorCode 보존 + 사용자 노출 표준화
- **파일**: `lib/core/network/dio_exception_handler.dart`
- **변경 내용**:
  - 서버 응답 에러(4xx/5xx)의 `messageKey`를 공통 `errorTemporaryRetry`로 통일하고, 백엔드 `errorCode`를 `code`에 그대로 저장
  - 백엔드 `detail`/`title`은 사용자 노출에서 제외(로그 전용) — 한국어 고정 응답이라 비-ko 로케일 오노출 방지
  - 미처리 분기(`422`, `429` 등)를 `statusCode` 유무로 분류하는 `_buildFallbackException` 추가
- **이유**: 정적 핸들러는 메시지를 직접 만들지 않고 "키 + errorCode"만 넘기고, 실제 다국어 변환은 UI 레이어 매퍼에 위임

#### 4. error_message_mapper — 3단계 우선순위 매핑
- **파일**: `lib/core/i18n/error_message_mapper.dart`
- **변경 내용**: `AppLocalizations` extension으로 다음 API 제공
  - `errorByException(e)`: ① 백엔드 errorCode → ② messageKey → ③ message 순 폴백
  - `shouldUseBackendErrorCode(e)`: `messageKey == 'errorTemporaryRetry'` + `code`가 `^[A-Z][A-Z0-9_]*$` 정규식 일치일 때만 true
  - `errorByCode(code)`: 60여 개 errorCode → ARB 메서드 매핑(누락 시 `errorTemporaryRetry` 폴백, non-null 보장)
  - `errorByKey(key, fallback)`: 네트워크/인증/Firebase 등 의미 기반 키 매핑
- **이유**: STOMP Notifier처럼 errorCode를 직접 보유한 곳은 `errorByCode`를, 일반 예외 흐름은 `errorByException`을 호출해 한 군데로 메시지 결정 로직을 모음

#### 5. 다국어 메시지 추가·정리 (ko/en/ja)
- **파일**: `lib/l10n/app_ko.arb`, `lib/l10n/app_en.arb`, `lib/l10n/app_ja.arb` (생성물: `app_localizations*.dart` 재생성)
- **변경 내용**: errorCode별 메시지 + 네트워크/인증 공통 키를 3개 로케일에 추가. 일본어 감옥 관련 용어를 `刑務所 → 牢屋`로 통일, `USER_NOT_FOUND` detail 오탈자(유저을→유저를) 수정
- **이유**: ARB가 i18n 정본 — 코드는 `flutter gen-l10n` 재생성으로 반영

#### 6. 소비 레이어 전환 (에러 분기·표시 교체)
- **파일**: `chat_provider.dart`, `game_event_provider.dart`, `lobby_provider.dart`, `deeplink_join_notifier.dart`, `waiting_room_page.dart`, `login_page.dart`, `deeplink_join_page.dart`, `game_settings_page.dart`, `game_settings_edit_page.dart`, `home_page.dart`, `agreement_error_handler.dart` 등
- **변경 내용**: 각 catch 블록·STOMP 에러 핸들러의 직접 메시지 조립을 `errorByException` / `errorByCode` 호출로 교체
- **이유**: 화면마다 흩어져 있던 에러 문구 결정을 매퍼 단일 경로로 수렴

#### 7. errorCode 카탈로그 문서화
- **파일**: `docs/error-codes.md`
- **변경 내용**: Common/Auth/User/Game/GameArea/Participant/Notice/GameResult/Report 도메인별 errorCode·status·title·detail 표 정리
- **이유**: 클라이언트·백엔드 공통 참조용 정본. "errorCode로 분기, detail은 fallback" 원칙을 명시

### 🔁 후속 정렬 — errorCode i18n 메시지를 백엔드 detail 기준으로 정정

#### 배경
초기 구현(위 5번)에서 ko ARB 메시지를 다듬은 paraphrase로 작성해 `docs/error-codes.md`의 `detail`과 불일치했다. 예) `INVALID_INVITE_CODE` → "잘못된 초대 코드입니다"(ARB) vs "입력하신 초대 코드가 유효하지 않습니다"(detail), `GAME_FULL` → "정원이 가득 찼습니다" vs "게임에 참가할 수 있는 최대 인원을 초과했습니다".

#### 원칙
`detail`(한국어 원문)을 정본으로 삼는다 → **ko = detail 원문**(끝 마침표만 제외), **en/ja = detail 번역**.

#### 변경 내용
- **파일**: `lib/l10n/app_ko.arb`, `app_en.arb`, `app_ja.arb` (생성물 `app_localizations*.dart` 재생성)
- **4xx 비즈니스 코드 약 45개**: ko를 docs detail 원문으로 정정, en/ja를 그 의미에 맞춰 재번역 (`USER_NOT_FOUND`, `INVALID_INVITE_CODE`, `GAME_FULL`, `GAME_NOT_FOUND` 등 게임/참가/신고/유저/약관/팀 전반)
- **5xx 내부/인프라 코드 9개** (`INTERNAL_SERVER_ERROR`·`FIREBASE_*`·`ENCRYPTION_*`·`*_GENERATION_FAILED` 등): 내부 기술 정보(암호화 키 규격, Firebase 설정 경로, 관리자 문의 안내) 노출 방지를 위해 공통 문구 "일시적인 오류가 발생했습니다…"로 **collapse 유지**. `@errorCodeInternalServerError` @주석에 정책 명시
- **기술 용어 6개** (`INVALID_DESTINATION`/STOMP, `UNSUPPORTED_MEDIA_TYPE`/Content-Type, `METHOD_NOT_ALLOWED`/HTTP 메소드, `ENDPOINT_NOT_FOUND`/URL·API, `EXPIRED_FIREBASE_TOKEN`·`INVALID_FIREBASE_TOKEN`/Firebase 토큰): jargon 노출 방지로 다듬은 문구 유지
- **`NOT_HOST`**: detail이 "게임을 시작할 수 있는…" 게임시작 전용 문구인데 설정/영역 수정 403에도 재사용됨 → 문맥 오류 방지 위해 "방장만 할 수 있습니다" 유지

**특이사항 (주의점)**:
- detail이 정본이지만 **기술 용어·내부 정보·문맥 재사용** 케이스는 의도적으로 예외 처리. 그 사유는 ARB `@`주석으로 남겨 "버그 아님"을 명시
- `docs/error-codes.md`·`api-docs.json`은 백엔드 정본이라 수정하지 않고 ARB를 거기에 맞췄다. `api-docs.json`의 `USER_NOT_FOUND` detail은 아직 오타(`유저을`)지만 백엔드 재생성물이라 미수정 — `docs/error-codes.md`·ARB는 `유저를`로 정정된 상태

#### 검증
- `flutter gen-l10n` 성공 (ARB 3종 JSON 유효), ko/en/ja 생성 파일 반영 확인
- `error_message_mapper_test.dart` 11개 통과 (테스트는 키 일치만 검증해 리터럴 값 변경의 영향 없음)
- 옛 리터럴 문구(`잘못된 초대 코드입니다` 등)를 검증하는 테스트 없음 → 회귀 없음

### 🔧 주요 변경사항 상세

#### 백엔드 errorCode vs Firebase provider code 구분
`shouldUseBackendErrorCode`의 핵심은 정규식 `^[A-Z][A-Z0-9_]*$`다. 백엔드 errorCode는 `GAME_FULL` 같은 대문자+언더스코어인 반면, Firebase provider code는 `invalid-credential` 같은 소문자+하이픈이라 정규식에서 자연스럽게 제외된다. 덕분에 같은 `code` 필드를 공유해도 인증 흐름의 messageKey 경로가 보존된다.

#### 매핑 누락 안전망
`errorByCode`는 switch에 없는 코드를 만나면 `errorTemporaryRetry`("잠시 후 다시 시도해주세요" 류 공통 문구)를 반환한다. 백엔드가 새 errorCode를 추가해도 클라이언트가 null/빈 문자열을 노출하지 않는다.

**특이사항 (주의점)**:
- ⚠️ **결합점**: `shouldUseBackendErrorCode`는 "서버 발 에러는 `DioExceptionHandler`가 항상 `messageKey='errorTemporaryRetry'`를 세팅한다"는 전제에 의존한다. 둘 중 한쪽을 바꾸면 이 가드가 깨지므로 함께 수정해야 한다.
- 백엔드 `detail`/`title`은 한국어 고정이라 **사용자 노출에 사용하지 않는다**(로그 전용). 비-ko 로케일 오노출 방지.
- ARB 키 추가 시 `errorByKey`/`errorByCode`의 switch에도 케이스를 더해야 한다(컴파일 타임 안전성을 위해 명시적 매핑 채택).

### 📌 참고사항

- ARB 수정 후 `flutter gen-l10n`(또는 build_runner) 재생성 필수 — `app_localizations*.dart` 직접 편집 금지
- **errorCode 메시지의 정본은 `docs/error-codes.md`의 `detail`**이다. ko는 detail 원문(끝 마침표 제외), en/ja는 detail 번역으로 맞춘다. 단 ① 기술 용어 포함, ② 5xx 내부 정보, ③ 문맥 재사용(NOT_HOST) 케이스는 예외이며 그 사유를 ARB `@`주석에 남긴다
- 신규 백엔드 errorCode가 추가되면: ① `docs/error-codes.md` 표 갱신 → ② ARB 3종에 detail 기준 메시지 추가 → ③ `error_message_mapper`의 `errorByCode` switch에 case 추가 → ④ gen-l10n 재생성
- STOMP 등 errorCode를 직접 보유한 흐름은 `errorByException`이 아닌 `errorByCode`를 직접 호출

# PRD V2

## 👮🏻‍♂️ '경찰과 도둑' 앱: 제품 요구사항 문서 (PRD)

- **문서 버전:** 1.1
- **최종 수정:** 2025년 11월 11일
- **작성자:** Gemini

### 1. 개요

본 문서는 오프라인 '경찰과 도둑' 놀이를 지원하는 모바일 애플리케이션의 제품 요구사항(PRD)을 정의합니다. 본 앱은 위치 기반 기술과 실시간 동기화를 통해 게임 운영을 자동화하고, 참가자들이 수동적인 조작 없이 게임의 전략과 즐거움에만 몰입할 수 있는 디지털 환경을 제공하는 것을 목표로 합니다.

### 2. 문제 정의 (Problem Definition)

현재 오프라인에서 진행되는 경찰과 도둑은 참가자들이 넓은 구역에서 서로를 추적하거나 도망치는 방식입니다. 하지만 게임의 핵심 요소인 위치 공유, 팀 식별, 게임 현황 파악이 모두 수동적(예: 단체 채팅방 스크린샷 공유)으로 이루어지고 있습니다.

이로 인해 다음과 같은 심각한 문제가 발생합니다.

- **위치 공유의 비효율성:** 정해진 시간마다 수동으로 위치를 캡처해 공유하는 과정이 번거로우며, 지도에 익숙하지 않은 참가자들은 직관적인 상황 파악이 어렵습니다.
- **게임 현황 파악의 어려움:** 누가 잡혔는지, 팀원이 누구인지, 남은 인원이 몇 명인지 실시간으로 파악할 수 있는 시스템이 부재하여 게임 몰입에 방해가 됩니다.
- **소통의 혼선:** 단일 외부 채팅방 사용으로 인해 팀 전략 노출 및 불필요한 정보 혼선이 발생합니다.
- **플레이그라운드 가시성 부족:** 실제 경기 구역 및 감옥 위치 표시가 없어 규칙 위반/이탈 분쟁이 빈번하게 발생합니다.

### 3. 핵심 목표 (Goals & Objectives)

본 프로젝트의 핵심 목표는 위치 기반 기술과 실시간 데이터 동기화를 통해, 참가자들이 오로지 게임의 전략과 즐거움에만 몰입할 수 있는 디지털 환경을 제공하는 것입니다.

- **운영 자동화:** 위치 공유, 참가자 상태(생존/탈락) 업데이트, 구역 이탈 감지를 100% 자동화하여 수동 개입을 제거합니다.
- **직관적 상황 인식:** 모든 참가자가 앱을 통해 5초 이내에 아군/적군의 위치(공유 시), 게임 구역, 남은 인원을 파악할 수 있는 통합 지도와 대시보드를 제공합니다.
- **전략적 소통 강화:** 팀별 전용 채널을 제공하여 소통의 혼선을 막고, 팀 전략 수립을 지원합니다.
- **공정성 확보:** 설정된 게임 구역을 시각적으로 제공하고, 이탈 시 즉각적인 알림을 통해 공정한 게임 진행을 보장합니다.

### 4. 사용자 역할 (User Roles)

- **방장 (Host):** 게임 세션을 생성하고, 규칙(구역, 시간)을 설정하며, 참가자를 초대합니다. 게임이 시작되면 방장 또한 '경찰' 또는 '도둑' 플레이어로 참여합니다.
- **경찰 (Police):** 도둑을 추적하고 '체포'하는 역할을 수행합니다. 주기적으로 공유되는 도둑의 위치(발자국)를 확인할 수 있습니다.
- **도둑 (Robber):** 경찰의 추적을 피해 제한 시간 동안 생존하는 것을 목표로 합니다. 본인의 위치가 주기적으로 경찰에게 노출됩니다.

### 5. MVP 핵심 기능 요구사항

### F1: 세션 관리 (Session Management)

게임의 생성, 참가, 시작을 관리하는 기능입니다.

| **기능 ID** | **기능** | **상세 요구사항** |
| --- | --- | --- |
| **F1.1** | **게임 생성** | 1. **진입:** 앱 홈 화면에서 '방 만들기' 버튼을 통해 진입합니다.
2. **순서:** F2.1 (구역 설정)을 먼저 완료해야 F1.2 (기본 설정) 화면으로 이동할 수 있습니다. |
| **F1.2** | **게임 설정 (방장)** | F2.1 완료 후 표시되는 설정 화면입니다.
1. **라운드 시간:** (필수) 게임의 총 진행 시간. (UI: 슬라이더 또는 숫자 입력, Default: 30분, 최소 10분/최대 180분)
2. **위치 공유 주기:** (필수) 도둑의 위치가 경찰에게 공개되는 주기. (UI: 슬라이더 또는 숫자 입력, Default: 5분, 최소 5분)
3. **경찰 대기 시간:** (부가) 게임 시작 후 도둑이 먼저 도망칠 수 있는 시간. (UI: 슬라이더 또는 숫자 입력, Default: 5분, 0분~15분)
4. **최대 인원:** (시스템 제한) 최대 30명으로 시스템 레벨에서 제한됩니다. (설정 항목 아님) |
| **F1.3** | **초대 코드** | 1. **생성:** F1.2 설정 완료 후 '초대 코드 생성하기' 버튼 클릭 시 자동 생성됩니다.
2. **형식:** 6자리 영문/숫자 조합 (예: A3B9D1), 입력 시 대소문자 구분 없음.
3. **공유:** '코드 복사', '공유' (OS 네이티브 공유 시트 호출 - QR, 메신저 전송) 기능을 제공합니다. |
| **F1.4** | **게임 참가** | 1. **진입:** 앱 홈 화면에서 '게임 참가' 버튼을 통해 진입합니다.
2. **입력:** F1.3에서 공유받은 초대 코드를 입력하는 UI를 제공합니다.
3. **에러 처리:** "유효하지 않은 코드입니다", "방이 꽉 찼습니다", "이미 시작된 게임입니다" 등의 명확한 에러 메시지를 표시합니다. |
| **F1.5** | **닉네임 설정** | 1. **시점:** F1.4 코드 입력 성공 후, F1.6 (대기실) 입장 전에 닉네임을 설정합니다.
2. **규칙:** 2~10자 이내 (한글, 영문, 숫자).
3. **중복 검사:** 해당 게임방 내에서 닉네임 중복을 실시간으로 검사하고, 중복 시 "이미 사용 중인 닉네임입니다" 메시지를 표시합니다. |
| **F1.6** | **대기실** | 1. **참가자 현황:** 입장한 모든 참가자의 닉네임 리스트를 표시합니다. (팀 미정 / 경찰 / 도둑 으로 구분)
2. **팀 선택:** 참가자는 '경찰' 또는 '도둑' 버튼을 눌러 본인의 팀을 직접 선택합니다. (팀 비율 제한 없음)
3. **준비 완료:** 모든 참가자(방장 포함)는 '준비 완료' 버튼을 눌러야 합니다. 버튼 클릭 시 위치 권한, GPS 활성화 여부를 체크하고, 미설정 시 설정으로 유도합니다.
4. **게임 시작 (방장):** 방장에게만 '게임 시작' 버튼이 보입니다. 이 버튼은 **모든 참가자가 팀 선택을 완료하고 '준비 완료' 상태**일 때만 활성화됩니다. |

### F2: 지도 및 위치 (Map & Location)

게임의 핵심인 지도 표시와 위치 기반 판정 기능입니다.

| **기능 ID** | **기능** | **상세 요구사항** |
| --- | --- | --- |
| **F2.1** | **구역 설정 (방장)** | F1.1에서 진입하는 지도 화면입니다.
1. **플레이 그라운드:** (필수) 지도 중심점을 지정한 후, 드래그를 통해 원형 경계의 크기를 조절하여 설정합니다. (최소/최대 반경 제한 필요)
2. **감옥:** (필수) 지도상의 특정 지점을 탭하여 감옥 구역(원형)을 설정합니다. (플레이 그라운드 내부에만 설정 가능)
3. **완료:** '구역 설정 완료' 버튼을 눌러야 경계 정보가 저장되고 F1.2로 이동합니다. |
| **F2.2** | **지도 UI (인게임)** | 게임이 시작된 후 모든 참가자에게 표시되는 기본 화면입니다.
1. **본인 위치:** 본인의 현재 위치가 실시간으로 지도에 표시됩니다 (예: 파란색 점).
2. **구역 시각화:** F2.1에서 설정된 '플레이 그라운드'와 '감옥'의 경계선이 명확하게 시각화되어 표시됩니다.
3. **아군 위치 (도둑):** 도둑은 다른 '생존' 상태의 도둑 팀원 위치를 실시간으로 확인 가능합니다.
4. **아군 위치 (경찰):** 경찰은 다른 경찰 팀원 위치를 **확인할 수 없습니다.** (전략적 소통 유도, MVP 단순화)
5. **상태 시각화:** '구속 중'인 도둑은 지도상에서 회색 마커 등으로 비활성화 처리됩니다. |
| **F2.3** | **위치 공유 (주기적)** | 1. **트리거:** F1.2에서 설정된 '위치 공유 주기' 타이머가 만료될 때마다 발동합니다.
2. **알림:** "도둑들의 위치가 공개되었습니다!" 전체 알림(배너)이 표시됩니다.
3. **데이터:** 발동 시점의 모든 '생존' 상태 도둑의 위치 좌표를 캡처합니다.
4. **표시 (경찰):** 경찰의 지도 위에 캡처된 위치가 '발자국' 아이콘 등으로 표시됩니다.
5. **표시 (도둑):** 도둑은 이 '발자국'을 볼 수 없습니다. (아군 실시간 위치만 확인 가능)
6. **유지:** '발자국'은 다음 공유 주기가 되어 새로운 '발자국'으로 갱신될 때까지 지도에 계속 표시됩니다. |
| **F2.4** | **위치 기반 감지** | 시스템이 참가자의 GPS 좌표를 기반으로 자동 판정합니다.
1. **구역 이탈 (플레이그라운드):** 참가자의 좌표가 '플레이 그라운드' 경계를 벗어날 경우, 즉시 해당 참가자에게 "경고: 구역을 이탈했습니다!" 개인 알림을 보냅니다.
2. **감옥 이탈 (도둑):**
    - **대상:** '구속 중' 상태인 도둑.
    - **판정:** '감옥' 구역을 30초 이상 연속으로 벗어날 경우 '실제 이탈'로 간주합니다.
    - **패널티 (이탈 시):**
        a. "감옥 이탈 감지! 도둑 OOO이(가) 탈출했습니다!" 전체 공지 알림.
        b. 해당 도둑의 위치를 10초간 모든 참가자(경찰/도둑)에게 실시간으로 노출시킵니다.
        c. 해당 도둑의 상태가 '구속 중' -> '생존'으로 변경됩니다. |

### F3: 핵심 게임 로직 (Core Game Logic)

게임의 진행, 승패, 상태 변화를 관리하는 기능입니다.

| **기능 ID** | **기능** | **상세 요구사항** |
| --- | --- | --- |
| **F3.1** | **게임 시작 흐름** | 1. **시작:** F1.6에서 방장이 '게임 시작' 버튼을 누르면 즉시 게임이 시작되며, 모든 참가자는 F2.2 (지도 UI) 화면으로 전환됩니다.
2. **도둑 도망:** '경찰 대기 시간'(F1.2)이 0보다 큰 경우, 해당 시간만큼의 타이머가 전체 화면에 표시됩니다.
    - 알림: "게임 시작! 도둑은 동안 도망칠 수 있습니다. 경찰은 대기하세요."
3. **추적 시작:** '경찰 대기 시간' 타이머가 00:00이 되면, **"경찰 이동 시작!"** 전체 공지(배너)가 표시되며 경찰의 본격적인 추적이 시작됩니다. (별도 카운트다운 없음) |
| **F3.2** | **체포 (Capture)** | 1. **트리거 (경찰):** 경찰 플레이어가 UI의 '체포하기' 버튼을 누릅니다.
2. **UI (경찰):** 현재 '생존' 상태인 모든 도둑의 닉네임 리스트가 팝업됩니다.
3. **액션 (경찰):** 경찰이 물리적으로 잡은 도둑의 닉네임을 리스트에서 선택합니다.
4. **상태 변경 (시스템):**
    a. 해당 도둑의 상태가 '생존' -> **'체포됨'**으로 즉시 변경됩니다.
    b. [경찰 개인 알림]: "OOO님을 체포했습니다."
    c. [도둑 개인 알림]: "체포되었습니다. 감옥으로 이동하세요."
    d. [전체 공지 알림]: "도둑 OOO이(가) 체포되었습니다." |
| **F3.3** | **감옥 (Jail)** | 1. **대상:** '체포됨' 상태의 도둑.
2. **의무:** 대상 도둑은 F2.1에서 설정된 '감옥' 구역으로 스스로 이동해야 합니다.
3. **트리거 (도둑):** '체포됨' 상태의 도둑이 '감옥' 구역 내부에 진입하면, '감옥 도착' 버튼이 활성화됩니다. 도둑이 이 버튼을 누릅니다.
4. **상태 변경 (시스템):**
    a. 해당 도둑의 상태가 '체포됨' -> **'구속 중'**으로 변경됩니다.
    b. [전체 공지 알림]: "도둑 OOO이(가) 감옥에 도착했습니다."
    c. [지도 UI]: 해당 도둑의 마커가 F2.2에 정의된 대로 (예: 회색) 변경됩니다. |
| **F3.4** | **게임 종료 조건** | 1. **조건 1 (시간 종료):** F1.2에서 설정한 '라운드 시간'이 모두 소진된 경우.
    - **승리:** **도둑 팀 승리** (한 명이라도 '생존' 또는 '체포됨' 상태로 남아있다면)
2. **조건 2 (도둑 전멸):** 모든 도둑이 '구속 중' 상태가 된 경우.
    - **승리:** **경찰 팀 승리**
3. **액션:** 두 조건 중 하나라도 만족하면 게임은 즉시 종료되며, "게임 종료! [경찰/도둑] 팀 승리!" 알림과 함께 결과 요약 화면으로 모든 참가자를 이동시킵니다. |

### F4: UI/UX 및 소통

사용자 경험을 보조하는 인터페이스 및 커뮤니케이션 기능입니다.

| **기능 ID** | **기능** | **상세 요구사항** |

## 결과 / 기록

- **게임 결과 조회 API** – 게임 종료 후 결과 요약(팀 승패, 체포 수 등)을 조회한다.
- **게임 기록 저장 API** – 게임 결과를 DB에 저장한다.
- **게임 기록 조회 API** – 사용자의 과거 게임 기록을 조회한다.

- **위치 / 지도 관리**
    - **1. 현재 위치 전송 API (클라이언트 → 서버)**
        - **역할:** 모든 플레이어가 3~5초마다 자기 GPS 위치를 서버에 실시간 전송한다. (공개 여부와 상관없이 계속 보냄)
        - **기술:** **WebSocket** (`updateLocation` 이벤트). 서버는 이 위치를 **Redis**에 갱신한다
    - **2. 경기 구역 정보 조회 API (클라이언트 → 서버)**
        - **역할:** 게임 시작 시, 설정된 '원형' 구역(경기장, 감옥)의 중심 좌표와 반지름을 서버에서 1회 받아온다.
        - **기술:** **REST API (GET)**. (예: `GET /api/game/{id}/area`)
    - **3. 위치 공개 트리거 API (서버 내부 로직)**
        - **역할:** '5분마다' 같은 정해진 주기를 세는 서버의 타이머이다.
        - **기술:** **서버 스케줄러 (Cron Job)**. 5분이 되면 4번을 실행시킨다.
    - **4. 도둑 위치 조회 API (서버 → 클라이언트)**
        - **역할:** 3번 트리거가 발동하면, 서버가 Redis에서 '도둑'들의 최신 위치를 꺼내 **모든 플레이어에게** 방송(Broadcast)한다.
        - **기술:** **WebSocket PUSH** (예: `revealRobbers` 이벤트). (클라이언트가 요청(조회)하는 API가 아님)
    - **5. 구역 이탈 감지 API (서버 내부 로직)**
        - **역할:** 1번(위치 전송)으로 좌표가 들어오는 즉시, 서버가 이 좌표가 '경기 구역' 원 안에 있는지 판정한다.
        - **기술:** **PostGIS** (`ST_DWithin` 함수 - '점'이 '원' 내부에 있는지 초고속 계산)
    - **6. 감옥 이탈 감지 API (서버 내부 로직)**
        - **역할:** 1번으로 좌표가 들어올 때, '구속 중' 상태인 도둑이 '감옥' 원을 벗어났는지 판정한다.
        - **기술:** **PostGIS** (`ST_DWithin` 함수).
    - PostGIS를 쓰는 이유
        
        
        1. **[지리 기능]** 1초에 수십 번씩 "A가 B 원 안에 있나?" (`ST_DWithin`)를 초고속 판별.
        2. **[관계형 기능]** '게임방', '유저', '팀', '채팅 내역', '체포 기록'을 안정적(ACID)으로 저장하고 **서로 연결(JOIN)**.
        
        | **비교 대상** | **유형** | **'경찰과 도둑' 앱 사용 시 치명적인 단점** |
        | --- | --- | --- |
        | **MySQL / MariaDB** | 범용 관계형 DB (RDBMS) | **[지리 기능] 탈락** (전문 공간 인덱스 부재로 인한 성능 부족) |
        | **MongoDB** | NoSQL (문서 DB) | **[관계형 기능] 탈락** (데이터 JOIN이 복잡해 무결성/통합성 저해) |
        | **Elasticsearch** | 검색 엔진 | **[관계형 기능] 탈락** (트랜잭션/ACID 지원 미흡으로 상태 저장 부적합) |
        | **PostGIS (+PostgreSQL)** | **전문 관계형 DB** | **(탈락 사유 없음)** (지리 기능과 관계형 기능 모두 완벽 지원) |
- **알림 / 소통**
    
    ### 서버 (Spring Boot)
    
    - Spring WebSocket: 웹소켓 구현을 위한 Spring 기본 모듈
    - STOMP: 웹소켓 위에서 동작하는 상위 프로토콜로, 주제(Topic) 단위 구독 및 메시지 전송을 지원
    - SimpMessagingTemplate: 서버에서 특정 주제를 구독 중인 클라이언트들에게 메시지를 전송하는 컴포넌트
    
    ### 클라이언트 (Flutter)
    
    - stomp_dart_client: Flutter에서 STOMP 프로토콜을 사용해 Spring 서버와 실시간 통신
    
    ### 기능별 구현 가이드라인
    
    1. 전체 공지 전송 (게임 이벤트)
        - 클라이언트는 특정 주제(`/topic/game/{gameId}/events`)를 구독
        - 서버는 게임 이벤트 발생 시 해당 주제로 메시지를 전송
        - 클라이언트는 수신된 메시지를 감지하여 알림 표시
    2. 전체 채팅 / 팀 채팅 전송
        - 클라이언트는 채팅 주제(`/topic/chat/game/{gameId}/all` 또는 `/topic/chat/game/{gameId}/team/{team}`)를 구독
        - 사용자가 메시지를 입력하면 `/app/chat/{team}` 목적지로 메시지 전송
        - 서버는 @MessageMapping으로 메시지를 수신 후 DB 저장
        - 이후 동일한 주제(`/topic/...`)로 브로드캐스트
        - 구독 중인 모든 팀원이 실시간으로 수신
    3. 팀 채팅 조회 (채팅 내역)
        - 과거 채팅 내역은 REST API로 처리
        - 클라이언트가 HTTP GET 요청
            
            예: `GET /api/chat/team/{team}/history?page=0&size=20`
            
        - 서버는 DB에서 해당 팀의 최근 메시지를 조회 후 JSON 응답
        - 클라이언트는 데이터를 화면에 표시하고, 이후 실시간 수신(WebSocket) 시작
    
    ### 요약
    
    | 기능 | 기술 | 통신 방식 | 설명 |
    | --- | --- | --- | --- |
    | 게임 이벤트 알림 | WebSocket (STOMP) | Push (Server-Side) | 서버가 특정 주제로 이벤트 발생 시 전송 |
    | 채팅 메시지 전송 | WebSocket (STOMP) | Push (Client-Side) | 클라이언트가 메시지를 목적지로 전송 |
    | 채팅 메시지 수신 | WebSocket (STOMP) | Push (Server-Side) | 서버가 받은 메시지를 팀원들에게 브로드캐스트 |
    | 채팅 내역 조회 | REST API (HTTP GET) | Pull | 클라이언트가 과거 데이터를 요청 및 표시 |
    
    ---
    
    핵심은 실시간성이 필요한 부분(이벤트, 채팅)은 WebSocket(STOMP)으로 처리하고,
    
    기록성 데이터(과거 내역, 설정 등)는 REST API로 처리하는 구조입니다.
    
    MVP(최소 기능 제품) 단계에서는 현재 설계 그대로 구현하고, 사용자가 늘어나면 Redis 같은 메시지 브로커를 추가하는 방식이 일반적입니다.
